- **共用 `Specification` 組裝器（同時支援 `MultiUserBaseEntity` 與 `ExpenseItem`）**：
  - 在 `OwnershipGuard` 抽出私有方法 `private <T> Specification<T> buildReadableSpec()`（內部依 `"ownerUserId"` 與 `"privacyLevel"` 欄位組合條件），對外提供：
    - `public <T extends MultiUserBaseEntity> Specification<T> readableSpec()`
    - `public Specification<ExpenseItem> readableExpenseSpec()`（供 `ExpenseServiceImpl.searchExpenseItems` 直接重用）
    - `public <T extends MultiUserBaseEntity> Specification<T> ownerSpec()`（產生 `ownerUserId = :currentUserId`）
- **單筆查詢下推至 SQL `WHERE` 層**：
  - 將 `OwnershipGuard.loadOwned`（`OwnershipGuard.java:72-77`）與 `loadReadable`（`OwnershipGuard.java:87-92`）簽章統一改為：
    ```java
    public <T extends MultiUserBaseEntity> T loadOwned(JpaSpecificationExecutor<T> repository, Long id) {
        Long requiredId = Objects.requireNonNull(id, "id must not be null");
        return repository.findOne(idEquals(requiredId).and(ownerSpec()))
                .orElseThrow(() -> new ItemNotFoundException("Resource not found with id: " + requiredId));
    }

    public <T extends MultiUserBaseEntity> T loadReadable(JpaSpecificationExecutor<T> repository, Long id) {
        Long requiredId = Objects.requireNonNull(id, "id must not be null");
        return repository.findOne(idEquals(requiredId).and(readableSpec()))
                .orElseThrow(() -> new ItemNotFoundException("Resource not found with id: " + requiredId));
    }
    ```
  - 保留 `Objects.requireNonNull(id, ...)` 防止 `id == null` 產生 `id = NULL` SQL；上游所有 Service 呼叫端無須改動，單筆查詢不再將他人資料撈進 Java 記憶體（僅 `ExpenseServiceImpl.getExpenseDetail` 因無獨立 Item Repository，維持 `entityManager.find()` 搭配 `requireReadable`）。

## 四、Phase 4 驗收標準
- 全專案再無任何 `@Filter`、`@FilterDef` 或 `session.enableFilter(...)` 程式碼。
- `X-View-Scope: FAMILY` 下，支援家族視角之列表 API（如 `GET /mortgages`、`GET /banks/transactions`、`GET /expenses`）正常回傳本人資料與家族成員非 `PRIVATE` 資料，且分頁總數正確；未帶該 Header 時只回傳本人資料（含單筆 `GET /{id}`）。
- `MultiUserIsolationArchTest` 於 Java 25 下正常執行並納入建置流程；在 Service 層新增無保護的 `findById`、`findAll()` 或 `EntityManager.find`/`createQuery` 會導致測試失敗。
- 全專案既有單元測試、既有與新增之跨使用者隔離整合測試全數通過。

## 五、待逐項討論拍板的設計方向

以下 7 項決策直接影響本階段實作方向，各有優缺點，討論確認後再定案：

### 討論 1：銀行餘額、銀行對帳單與 NISA 定期設定之視角邊界（僅本人 vs 支援 `X-View-Scope: FAMILY`）
- **涉及端點**：
  - `BankTransactionServiceImpl.getLatestBankBalances()`（`GET /banks/balances`，回傳 `Map<String, Integer>`，key 僅為 `bankName`）
  - `BankTransactionServiceImpl.getStatement(bankName, statementMonth)`（`GET /banks/statements/{bankName}/{statementMonth}`）
  - `NisaContributionSettingServiceImpl.getAllSettings()`（`GET /assets/nisa/settings`，目前 `NisaContributionSettingController.java:47-52` 未傳 `currentUserId` 給 Mapper 做隱私遮罩）
- **選項 A（鎖定本人 `ownerUserId`）**：
  - 優點：避免兩位家人皆有同名銀行（如 `"SMBC"`）時 `Map<String, Integer>` 發生 key 覆蓋或 `getStatement` 查出多筆報 `NonUniqueResultException`；NISA 定期扣款設定不需額外改造 Controller 遮罩。
  - 缺點：家族視角下無法看到家人的銀行各行餘額與 NISA 定期扣款設定。
- **選項 B（支援 `X-View-Scope: FAMILY`）**：
  - 優點：家族視角下畫面覆蓋更完整。
  - 缺點：`getLatestBankBalances()` 須改寫為「依 `(ownerUserId, bankName)` 各取最新餘額後再依銀行名加總（或改變回傳結構）」並釐清 `AGGREGATE_ONLY` 是否計入；`getStatement` 在同銀行同月可能回傳多筆須改動簽章；`NisaContributionSettingController` 須同步補上 `PrivacyMaskingUtil` 遮罩。

### 討論 2：`DefinedContributionServiceImpl.deleteAllSnapshots()` 與 `resetSequence()` 的去留
- **現況**：`DefinedContributionController.java:148-157` 在 `DELETE /assets/dc` 未帶 `recordDate` 時呼叫 `DefinedContributionServiceImpl.deleteAllSnapshots()`（`L185-201`），執行 `dcRepository.deleteAll()` 並呼叫 `ALTER TABLE dc_account_snapshot / dc_fund_snapshot AUTO_INCREMENT = 1`。
- **選項 A（改為僅刪除當前使用者快照，並移除兩支 `resetSequence()`）**：
  - 優點：保留 API 介面，同時改以 `findAllByOwnerUserId(currentUserId)` 搭配 `dcRepository.deleteAll(snapshots)` 安全觸發 `CascadeType.ALL` 清理子表，不影響其他使用者與全域自增序號。
  - 缺點：須確認多使用者環境下是否仍需要一鍵清空本人全部 DC 快照的能力。
- **選項 B（移除無條件全刪分支，`DELETE /assets/dc` 改為強制要求 `recordDate` 或僅保留 `DELETE /assets/dc/{id}`）**：
  - 優點：徹底消除誤觸全刪風險與無用 native SQL。
  - 缺點：若前端有呼叫不帶參數的 `DELETE /assets/dc` 按鈕，須同步調整前端。

### 討論 3：單筆 `requireReadable` 切齊 `ScopeResolver` 後的兩個語意確認
- **3a — `CategoryServiceImpl.createCategory`／`updateCategory` 綁定 `parentId`（`CategoryServiceImpl.java:71,93`）**：
  - 選項 1（改為 `loadOwned`）：只允許將自己的分類設為父分類。優點：避免家人刪除分類或將其改為 `PRIVATE` 時破壞自己的分類樹結構。缺點：不可跨人引用家人 `SHARED` 分類作父分類。
  - 選項 2（維持 `loadReadable`）：僅在請求帶 `X-View-Scope: FAMILY` 時允許引用家人 `SHARED` 分類。優點：保留跨家族共享分類階層彈性。缺點：寫入端點（`POST`/`PUT`）行為隨讀取用 Header 改變，較不直覺。
- **3b — 無家族使用者帶 `X-View-Scope: FAMILY` 請求單筆端點（如 `GET /insurance-policies/{id}`）之狀態碼**：
  - 選項 1（沿用 `ScopeResolver.java:78` 回傳 `403 FORBIDDEN`）：與所有列表端點完全一致，無須特例處理。
  - 選項 2（於 `OwnershipGuard` 捕捉 `FORBIDDEN` 轉為 `ItemNotFoundException` 回傳 `404`）：嚴格維持單筆端點統一回傳 `404`，但與列表端點狀態碼分歧。

### 討論 4：三個 `UserSettings` CRUD Service 回傳之 `ownerUserId` 欄位
- **現況**：`SalaryUserSettingsServiceImpl.java:42,65`、`NisaUserSettingsServiceImpl.java:38,52`、`DefinedContributionUserSettingsServiceImpl.java:51,98,136,145` 目前均呼叫 `fromEntity(settings, null)`。
- **選項 A（改傳 `currentUserId`）**：
  - 優點：`Result.ownerUserId` 與其他所有領域一致，避免日後 Mapper 套用 `PrivacyMaskingUtil.shouldMask(currentUserId, result.getOwnerUserId(), ...)` 時因 `null` 誤把使用者自己的設定遮罩。
  - 缺點：回應物件中的 `ownerUserId` 由 `null` 變為實際使用者 ID（須確認無測試斷言其為 `null`）。
- **選項 B（維持傳 `null`）**：
  - 優點：對回應內容零變動。
  - 缺點：留下一處與其他 Service 不一致的特例。

### 討論 5：防線強度 — 僅採 ArchUnit，或加做編譯期窄介面（`MultiUserRepository`）？
- **選項 A（僅採 ArchUnit）**：
  - 優點：改動成本低、不影響 Spring Data 標準介面與整合測試清理（`deleteAll()`），CI 可自動擋下違規。
  - 缺點：屬測試期檢查，IDE 自動補全仍看得到 `findById`／`findAll()`。
- **選項 B（ArchUnit ＋ `MultiUserRepository<T, Long>` 編譯期窄介面）**：
  - 優點：從編譯期與 IDE 自動補全徹底隱藏無條件方法，防誤用強度最高。
  - 缺點：須重構所有 20+ 個多使用者 Repository 介面並另行處理整合測試 teardown 清理方式，改動面較大。

### 討論 6：待棄用本機掃檔 `execute()` 編譯相容性與 `ImportTaskController`／`SecurityUtil` 處置
本機資料夾掃描排程即將移除，且網頁手動觸發本機掃檔僅系統管理員可用（他人無法將檔案放置於伺服器本機路徑），因此不做多使用者隔離重構；但本階段刪除舊無條件 Repository 方法時，須就以下兩點擇一處理以避免編譯失敗或安全漏洞：
- **6a — `ImportTaskController.java:82` 與 `SecurityUtil.getCurrentUserId()`**：
  - 選項 1（**不放寬 `SecurityUtil`**，將 `ImportTaskController.java:79-98` 改用 `DelegatingSecurityContextRunnable` 直接傳遞 `JwtAuthenticationToken`，比照 `TransactionSourceTaskController.java:95`）：
    - 優點：完全不動核心安全工具 `SecurityUtil.java:47-53`，**徹底避免誤接受 Spring Security `AnonymousAuthenticationToken`（其 `isAuthenticated()` 為 `true` 且 `principal` 為 `"anonymousUser"` 字串）的安全漏洞**；管理員觸發 `POST /import/tasks` 仍能正確傳遞 JWT。
    - 缺點：須調整 `ImportTaskController.java:79-98` 的非同步包裝與 `progress` 更新區塊。
  - 選項 2（修改 `SecurityUtil.getCurrentUserId()` 支援 `UsernamePasswordAuthenticationToken`）：
    - 優點：不動 `ImportTaskController`。
    - 缺點：放寬安全工具類，實作時**必須**嚴格限定 `authentication instanceof UsernamePasswordAuthenticationToken && authentication.isAuthenticated() && authentication.getPrincipal() instanceof String str && !str.isBlank()`（絕不可比照 `SpringSecurityAuditorAware.java:42-45` 只檢查 `isAuthenticated() && principal instanceof String`，否則會放行 `AnonymousAuthenticationToken`），且須同步更新 `SecurityUtilTest.java:102-110`。
- **6b — 刪除舊無條件 Repository 方法時，殘留 `*JobServiceImpl.execute()` 的編譯處理**：
  - 選項 1（暫時保留僅供 `execute()` 呼叫的少數舊方法並列入 ArchUnit 白名單，待排程整批移除時一併刪除）：
    - 優點：完全不花工時修改即將淘汰的排程程式碼。
    - 缺點：在排程移除前，Repository 與 ArchUnit 會留有過渡期白名單。
  - 選項 2（將 `*JobServiceImpl.execute()` 內查詢同步改為帶 `SecurityUtil.getCurrentUserId()` 的新方法，本階段立即刪光所有舊無條件方法）：
    - 優點：Repository 與 ArchUnit 一次乾淨到位、零例外白名單；管理員手動觸發時也會自動帶入本人 `userId`。
    - 缺點：無 JWT 的排程執行緒觸發時會直接拋 401（在排程即將移除的前提下通常可接受）。

### 討論 7：`app.security.enabled=false` 本機開發模式之行為策略
- **現況**：`application.properties:54` 預設 `app.security.enabled=false`（`SecurityConfig.java:80-87` 放行所有請求且不產生 `JwtAuthenticationToken`）。過去 `OwnerFilterInterceptor` 遇到 `userId == null` 會靜默跳過；本階段移除 Filter 且所有列表全面改走 `readableSpec()` → `SecurityUtil.getCurrentUserId()` 後，未帶 JWT 的本機請求將全面回傳 `401 UNAUTHORIZED`。
- **選項 A（維持嚴格要求驗證身分，不做特殊放行）**：
  - 優點：確保開發環境與正式環境權限路徑一致，不再掩蓋認證／隔離缺陷。
  - 缺點：本機手動呼叫 API 時須啟用驗證並帶有效 JWT。
- **選項 B（僅在 `app.security.enabled=false` 時啟用 dev-only 模擬使用者 Filter）**：
  - 優點：維持不接 Auth Server 也能本機直打 API 的便利性。
  - 缺點：須嚴格限定 `@ConditionalOnProperty(name = "app.security.enabled", havingValue = "false")` 並做好防護，避免誤設定流入正式環境。
