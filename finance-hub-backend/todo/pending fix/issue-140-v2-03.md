# Issue 140 v2 — Phase 3：列表查詢顯式化、防繞過防線與移除 Filter

> 前置條件：完成 [issue-140-v2-01.md](file:///Users/edward/Desktop/Projects/youtube-data-hub-wrapper/finance-hub/finance-hub-backend/todo/pending%20fix/issue-140-v2-01.md) 與 [issue-140-v2-02.md](file:///Users/edward/Desktop/Projects/youtube-data-hub-wrapper/finance-hub/finance-hub-backend/todo/pending%20fix/issue-140-v2-02.md)。總覽見 [issue-140-v2.md](file:///Users/edward/Desktop/Projects/youtube-data-hub-wrapper/finance-hub/finance-hub-backend/todo/pending%20fix/issue-140-v2.md)。

## 目標
1. 將所有仍依賴 Hibernate Filter 的列表查詢、統計與衍生查詢改為顯式 SQL 條件，讓全系統資料存取規則完全一致。
2. 建立編譯期／建置期防誤用機制，防止日後開發者繞過 `OwnershipGuard` 或誤用無條件查詢。
3. 安全退場並移除 Hibernate `@Filter` 機制。

---

## 一、將列表與衍生查詢改為顯式邊界（取代 Filter）

> **動手前盤點步驟**：開始改寫前，先全專案搜尋所有 `extends MultiUserBaseEntity` 的實體及其對應 Repository 介面，逐一列出所有無條件 `findAll`、衍生查詢與 `@Query` 清單，再進行批次替換（避免遺漏）。

1. **一般列表查詢（支援個人／家族視角切換）**：
   - 繼承 `MultiUserBaseEntity` 的 Repository 補上 `JpaSpecificationExecutor<T>`。
   - Service 層將原本無條件的 `repository.findAll()` / `repository.findAll(pageable)` / `repository.findAll(sort)`，改為呼叫 `repository.findAll(ownershipGuard.readableSpec(), ...)`。
   - 過濾發生在 SQL `WHERE` 層，分頁（`Pageable`）、排序（`Sort`）與 `count` 皆可正常運作。
2. **衍生查詢與自訂 `@Query`**：
   - 全專案盤點所有繼承 `MultiUserBaseEntity` 的 Repository 介面內，不帶 `ownerUserId` / `familyUserIds` 條件的衍生方法（如 `findAllBy...`、`findFirstBy...`、`countBy...`）與 `@Query` 方法。
   - 依業務性質改為只限本人（傳入 `currentUserId`）或支援家族視角（傳入 `ScopeResolver` 解析出的 `ownerUserIds` 與隱私條件）。
3. **手動觸發的背景匯入 Job**（`ImportTaskController`、`TransactionSourceTaskController`，見 `issue-140.md:L298-L304`）：
   - 因已於 Phase 1 將 `ScopeResolver` 設計為在非 HTTP 執行緒預設回傳個人 Scope，只要背景執行緒內有設定 `SecurityContext`（帶 `userId`），呼叫 `OwnershipGuard` 或 `readableSpec()` 就會自動且明確地鎖定該使用者的個人資料，不再受限於 HTTP Session Filter 無法跨執行緒的問題。
   - **已確認的相容改法**：`TransactionSourceTaskController.java:95` 使用 `DelegatingSecurityContextRunnable` 會直接傳遞 `JwtAuthenticationToken`；而 `ImportTaskController.java:82` 則是在背景執行緒建立 `new UsernamePasswordAuthenticationToken(userId, null, List.of())`（principal 為 `String`）。因此 `SecurityUtil.getCurrentUserId()`（`SecurityUtil.java:49`）須比照 `SpringSecurityAuditorAware.java:42-45`，在 `JwtAuthenticationToken` 之外一併支援 `authentication.isAuthenticated() && authentication.getPrincipal() instanceof String str`。
4. **將單筆 `OwnershipGuard.loadOwned`／`loadReadable` 升級為 SQL 層過濾**：
   - 待所有繼承 `MultiUserBaseEntity` 的 Repository 都補上 `JpaSpecificationExecutor<T>` 後，將 `OwnershipGuard` 內的 `loadOwned` 與 `loadReadable` 參數由 `JpaRepository<T, Long>` 改為 `JpaSpecificationExecutor<T>`（內部改呼叫 `findOne(idEquals(id).and(...))`，找不到或無權限一樣丟 `ItemNotFoundException`）。
   - **注意主鍵泛型 `<ID>`**：Phase 2 涵蓋的 11 個資源主鍵皆為 `Long`，但全專案內如 `BankTransaction`、`NisaContributionSetting`、`ETradeAccountSnapshot` 的主鍵為 `String`，因此簽章應設計為 `<T extends MultiUserBaseEntity, ID> T loadOwned(JpaSpecificationExecutor<T> repository, ID id)`（`loadReadable` 亦同）。
   - 上游 11 個 Service 的呼叫端一行都不用改，單筆查詢的擁有者與家族條件正式下推至 SQL `WHERE` 層，不再把他人資料列撈進 Java 記憶體（僅 `ExpenseServiceImpl.getExpenseDetail` 因無獨立 Repository，維持 `entityManager.find()` 搭配 Java 層 `requireReadable`）。

## 二、建立防誤用／防繞過防線

為避免日後新增端點時有人不小心又呼叫無條件的 `findById`、`findAll` 或 `entityManager.find`，以 **ArchUnit 架構測試為必選預設**，編譯期窄介面為可選強化：

1. **架構測試（ArchUnit，必選，成本低、CI 自動阻擋）**：
   - 新增一條 ArchUnit 測試規則：
     - 所有 `MultiUserBaseEntity` 子類別的 Repository，禁止在 `Service` 層直接呼叫 `CrudRepository.findById`、`deleteById`、`findAll()`（無參數版）。
     - 禁止在 `Service` 層直接呼叫 `EntityManager.find`（除明確列入白名單且有搭配 `OwnershipGuard` 檢查的 `ExpenseServiceImpl` 之外）。
2. **編譯期窄介面（可選進階強化，強度最高）**：
   - 若要從編譯期徹底封鎖，可為多使用者實體建立自訂的基礎 Repository 介面（例如 `MultiUserRepository<T, ID>`，繼承 `Repository<T, ID>` 與 `JpaSpecificationExecutor<T>`），僅重新暴露安全的方法（`save`、`saveAll`、`delete`、`deleteAll` 等常用寫入／刪除簽章與帶 `ownerUserId` 的方法），不再直接繼承暴露無條件 `findById` / `deleteById` / `findAll` 的 `JpaRepository`。

## 三、移除 Hibernate Filter（退場步驟）

確認上述所有查詢皆已切換為顯式邊界，且 ArchUnit／整合測試全數通過後，再執行以下清理：

1. 移除 `OwnerFilterInterceptor.java:63-87` 中呼叫 `entityManager.unwrap(Session.class)` 與 `session.enableFilter(...)` 的邏輯（若不再需要攔截器，可一併從 `WebMvcConfig.java:48` 移除註冊；`ExtensionSecurityInterceptor.java` 仍可保留作為 fail-fast 防護）。
2. 移除 `MultiUserBaseEntity.java:51-58` 上的 `@FilterDef`（`ownerFilter`、`personalFilter`、`familyFilter`）與 `@Filter` 註解。

## 四、Phase 3 驗收標準
- 全專案再無任何依賴 Hibernate `@Filter` 的查詢路徑。
- `X-View-Scope: FAMILY` 下，列表 API（如 `GET /mortgages`）仍正常回傳本人資料與家族成員的 `SHARED` 資料，且分頁筆數正確。
- ArchUnit 架構測試納入 CI，嘗試在 Service 新增無保護的 `findById` 或 `entityManager.find` 會直接導致建置失敗。
- 現有測試與新增的跨使用者隔離測試全數通過。
