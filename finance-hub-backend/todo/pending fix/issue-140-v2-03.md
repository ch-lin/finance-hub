## 目標與範圍邊界

1. 將 Phase 1 與 Phase 2 尚未涵蓋的**正式多使用者 HTTP／Chrome Extension 業務模組**全數改採顯式 `ownerUserId` 或 `OwnershipGuard`／`ScopeResolver` 邊界，包含：對帳（Reconciliation）、模擬計算器（`IncomeExpenseCalculator`）、NISA 試算、信用卡交易與帳單、E-Trade 公司股票、Amazon／Rakuten／Sofmap Chrome Extension、DC 瀏覽器檔案上傳與匯入歷史查詢，直接修補現有的單筆 IDOR、跨使用者查詢外洩，並消除對隱式 Hibernate `@Filter` 的依賴。
2. 修正本階段涉及的多使用者 Repository 中錯誤宣告為 `String` 主鍵泛型的介面（實體皆繼承 `MultiUserBaseEntity` → `BaseEntity` 之 `Long id`），並為本階段需改用 `Specification` 列表查詢的 8 個 E-Trade Repository 補上 `JpaSpecificationExecutor<T>`。
3. 將僅剩未納入 `owner_user_id` 的 4 個多使用者實體全域唯一鍵（`BaseOrder` 及其三張購物訂單表與 `InsurancePolicy`）改為含 `owner_user_id` 之複合唯一鍵，與其餘多使用者實體對齊。
4. **不在本階段範圍內**：
   - 本機資料夾掃描排程與伺服器本機掃檔觸發（`*JobServiceImpl.execute()`）屬於規劃整批移除的過渡期匯入方式，且僅系統管理員可將檔案置於伺服器本機路徑，因此本階段不對其進行多使用者隔離改造。
   - `AmazonServiceImpl.cleanup()`、`RakutenServiceImpl.cleanup()` 與各 Repository 宣告的 `cleanTable()`／`resetSequence()` 保留作為**系統管理員專用測試／重置工具**（後續另以管理員角色權限保護，不於本階段移除或改寫；若未來需提供一般使用者清空個人資料功能，另開獨立 issue／plan 規劃）。

### 6. 補齊剩餘 4 個多使用者實體之 `owner_user_id` 複合唯一鍵

- **現況風險**：全專案有唯一鍵約束的多使用者實體中，`BankStatement`、`CreditCardStatement`、`DefinedContributionAccountSnapshot`、`SalaryRecord`、`PensionRecord`、`NisaSnapshotRecord`、`NisaContributionSetting` 與 E-Trade 實體皆已包含 `owner_user_id`，僅剩以下 4 個實體仍為全域唯一鍵，導致不同使用者寫入相同測試單號或保單號時在資料庫層觸發唯一鍵衝突：
  - `BaseOrder.java:105`（`@Column(name = BaseOrder.ORDER_ID_COLUMN, nullable = false, unique = true)`）與 `AmazonOrder.java:46`、`RakutenOrder.java:42`、`SofmapOrder.java:46`（`@UniqueConstraint(columnNames = BaseOrder.ORDER_ID_COLUMN)`）。
  - `InsurancePolicy.java:32-36`（`@UniqueConstraint(name = "uk_insurance_policy_company_number", columnNames = { "company_name", "policy_number" })`）。
- **明確改法**：
  1. **`BaseOrder.java:105`**（`hub-domain/src/main/java/ch/lin/finance/hub/backend/api/domain/model/accounting/shopping/BaseOrder.java`）：移除 `@Column` 上的 `unique = true`（避免 Hibernate 仍對 `order_id` 單欄建出全域唯一索引）。
  2. **`AmazonOrder.java:46`、`RakutenOrder.java:42`、`SofmapOrder.java:46`**：將 `@UniqueConstraint` 改為 `columnNames = { MultiUserBaseEntity.OWNER_USER_ID_COLUMN, BaseOrder.ORDER_ID_COLUMN }`。
     - **索引說明**：MySQL（InnoDB）與 H2 會自動為此複合唯一約束建立 `(owner_user_id, order_id)` B-Tree 唯一索引；多使用者架構下所有訂單／記帳查詢皆帶 `owner_user_id`（個人 `=` 或家族 `IN`），因此 `owner_user_id` 篩選、`(owner_user_id, order_id)` 精確查詢與前綴搜尋皆會直接命中此複合索引，無須額外重複建立單欄 `order_id` 索引。
  3. **`InsurancePolicy.java:32-36`**（`hub-domain/src/main/java/ch/lin/finance/hub/backend/api/domain/model/accounting/insurance/InsurancePolicy.java`）：將 `uk_insurance_policy_company_number` 改為 `columnNames = { MultiUserBaseEntity.OWNER_USER_ID_COLUMN, "company_name", "policy_number" }`。
- **無須 Schema Migration 腳本說明**：本系統目前尚未上線，且 **MySQL 資料庫尚未正式建置**（目前測試環境使用每次自動重建的 H2），因此直接調整 JPA `@UniqueConstraint` 註解即可，刻意不撰寫額外的資料庫遷移或 `DROP INDEX` SQL 腳本，並非遺漏。

## 三、Phase 3 驗收標準

- 上述第一、二節所列所有正式 HTTP／Chrome Extension 業務模組皆改採顯式 `ownerUserId` 或 `OwnershipGuard`／`ScopeResolver` 過濾，不再依賴隱式 Hibernate `@Filter`。
- 新增／更新跨使用者隔離整合測試，驗證：
  1. `GET /reconciliation/{transactionId}/suggestions` 與 `POST /reconciliation/link` 傳入他人 ID 一律回傳 `404`（不透過 `already linked` 錯誤訊息暴露他人資料存在）。
  2. `GET /credit-cards/transactions`、`GET /credit-cards`、`GET /credit-cards/total-amounts` 在個人模式下僅呈現本人資料；在 `X-View-Scope: FAMILY` 下涵蓋本人與家族成員之 `SHARED` 及 `AGGREGATE_ONLY`（並將兩者併入各卡 total），同時排除家族成員之 `PRIVATE` 資料。
  3. `GET /assets/company-stock/etrade*`、`GET /amazon/extension/{orderId}`、`GET /assets/nisa/projection`、`GET /tasks/{source}/history` 跨使用者皆不外洩他人資料。
  4. 兩位不同使用者分別儲存相同 `orderId`（Amazon／Rakuten／Sofmap）與相同 `(companyName, policyNumber)`（`InsurancePolicy`）皆能成功寫入而不觸發唯一鍵衝突。
  5. `AssetSimulationFamilyIsolationIntegrationTest` 補入雙方銀行交易、信用卡交易與不同 `salaryGrowthRate`，驗證在 `X-View-Scope: FAMILY` 下模擬結果依然與個人模式一致、不受家人資料污染。
- 全專案既有測試與新增測試全數通過。
