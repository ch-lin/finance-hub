## 目標與範圍邊界

1. 將 Phase 1 與 Phase 2 尚未涵蓋的**正式多使用者 HTTP／Chrome Extension 業務模組**全數改採顯式 `ownerUserId` 或 `OwnershipGuard`／`ScopeResolver` 邊界，包含：對帳（Reconciliation）、模擬計算器（`IncomeExpenseCalculator`）、NISA 試算、信用卡交易與帳單、E-Trade 公司股票、Amazon／Rakuten／Sofmap Chrome Extension、DC 瀏覽器檔案上傳與匯入歷史查詢，直接修補現有的單筆 IDOR、跨使用者查詢外洩，並消除對隱式 Hibernate `@Filter` 的依賴。
2. 修正本階段涉及的多使用者 Repository 中錯誤宣告為 `String` 主鍵泛型的介面（實體皆繼承 `MultiUserBaseEntity` → `BaseEntity` 之 `Long id`），並為本階段需改用 `Specification` 列表查詢的 8 個 E-Trade Repository 補上 `JpaSpecificationExecutor<T>`。
3. 將僅剩未納入 `owner_user_id` 的 4 個多使用者實體全域唯一鍵（`BaseOrder` 及其三張購物訂單表與 `InsurancePolicy`）改為含 `owner_user_id` 之複合唯一鍵，與其餘多使用者實體對齊。
4. **不在本階段範圍內**：
   - 本機資料夾掃描排程與伺服器本機掃檔觸發（`*JobServiceImpl.execute()`）屬於規劃整批移除的過渡期匯入方式，且僅系統管理員可將檔案置於伺服器本機路徑，因此本階段不對其進行多使用者隔離改造。
   - `AmazonServiceImpl.cleanup()`、`RakutenServiceImpl.cleanup()` 與各 Repository 宣告的 `cleanTable()`／`resetSequence()` 保留作為**系統管理員專用測試／重置工具**（後續另以管理員角色權限保護，不於本階段移除或改寫；若未來需提供一般使用者清空個人資料功能，另開獨立 issue／plan 規劃）。
