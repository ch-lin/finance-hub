# [FIXED] Issue 155：信用卡對帳單重新匯入完全沒有任何合併/覆蓋保護，跟其他所有匯入來源的做法都不一樣，重新匯入同一期帳單會直接整筆失敗、資料全部遺失

## 這份issue怎麼被發現的
這是這次Source Code Review針對匯入解析器的業務邏輯進行商業邏輯審查時發現的問題。這是重新匯入時的合併邏輯，不是對CSV/HTML格式本身的猜測。

## 相關檔案
- `finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/accounting/creditcard/CreditCardServiceImpl.java:191-193`（批次匯入：`if (statement != null) { statementRepository.save(statement); }`）
- 同檔案`:268-269`（單檔匯入：`statementRepository.save(Objects.requireNonNull(statement));`）
- `finance-hub/finance-hub-backend/hub-domain/src/main/java/ch/lin/finance/hub/backend/api/domain/model/accounting/creditcard/CreditCardStatement.java:52-55`（`(ownerUserId, cardName, billingMonth)`這組唯一性限制）
- `finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/repository/accounting/creditcard/CreditCardStatementRepository.java:44`（`findByCardNameAndBillingMonth`這個查詢方法已經存在，但匯入流程完全沒有呼叫它）
- 對照：`BankTransactionServiceImpl.saveStatement()`（依`findByBankNameAndStatementMonth`查詢既有紀錄、合併新交易）、`SalaryJobServiceImpl`（依`findByPaymentDate`查詢並就地更新）、`PensionJobServiceImpl`/`SbiNisaJobServiceImpl`/`CompanyStockJobServiceImpl`（先`deleteByRecordDate`再新增）、`DefinedContributionJobServiceImpl`（依`findByRecordDateAndType`查詢並呼叫`.merge(...)`）、`MortgageJobServiceImpl`（依`loanName`查詢並呼叫`updateMortgage`）——這六個匯入來源，每一個都有自己的「重新匯入該怎麼處理既有資料」邏輯，只有信用卡對帳單完全沒有

## 現狀
兩個信用卡匯入進入點都是直接`new CreditCardStatement(...)`後`.save(...)`，完全沒有先查詢是否已經存在同一張卡、同一個帳單月份的既有紀錄。`findByCardNameAndBillingMonth`這個查詢方法確實存在，而且正確地被用在別的地方（手動新增單筆交易時的查詢），但完全沒有被匯入流程呼叫。

## 為何是問題
只要同一張卡、同一個帳單月份的CSV被重複匯入第二次——不管是使用者自己刻意重新下載帳單想補上新產生的交易（這正是銀行、薪資、房貸等其他來源都支援的「重新匯入=更新/修正」工作流程），還是意外重複匯入（例如排程job的檔案移動因為暫時性IO錯誤失敗，造成同一份檔案留在來源資料夾、下次掃描又被重新處理一次）——都會直接撞到資料庫的唯一性限制，拋出例外。這個例外被外層一個通用的`catch (Exception e)`攔住，整張對帳單（連同裡面全部的交易明細）直接整筆存檔失敗，不是部分重複，是這次重新匯入帶來的所有資料全部遺失，而且錯誤訊息只是原始的資料庫例外訊息，不會告訴使用者「這其實是同一期帳單已經匯入過」。

## 建議修正方向
這裡列出可能的方向，不代為決定：

**方向A：依(卡名,帳單月份)查詢既有紀錄，合併新交易進去**
- 做法：仿照銀行對帳單`BankTransactionServiceImpl.saveStatement()`已經驗證過的做法。
- 優點：跟既有、已經證實可行的模式一致。
- 缺點：`CreditCardTransaction.equals()`目前是依(卡名、交易日期、商店名、金額)判斷相同——如果同一天同一家店有兩筆金額剛好相同、但實際上是兩筆不同的交易，合併時可能會誤判成同一筆、讓第二筆被悄悄忽略（這個風險銀行對帳單那邊本來就存在、目前被接受）。

**方向B：先刪除既有的整張對帳單，再整批重新寫入**
- 做法：仿照NISA/年金/公司股票匯入已經驗證過的「先刪後存」做法。
- 優點：簡單、確定性高，資料庫裡的內容永遠跟最新一次匯入的CSV完全一致。
- 缺點：如果使用者曾經手動替某一筆信用卡交易指定分類(`CreditCardTransaction.category`可以手動設定)，整張刪除重建會把這些手動分類全部清空，強迫使用者整張帳單重新分類一次。

**方向C：至少先攔截這個特定的例外，給一個清楚的訊息**
- 做法：專門攔截這個唯一性違反例外，回傳「這一期帳單已經匯入過」而不是原始的資料庫錯誤訊息。
- 優點：改動最小，馬上改善診斷體驗。
- 缺點：沒有真正解決「重新匯入想補上新交易」這個正當需求，使用者仍然沒辦法用重新匯入的方式去修正或補齊資料。

### 二、信用卡交易的不可分割性與合併的根本矛盾

在現實日常消費中，「同日、同店、同金額」是極其普遍的真實情境（例如：自動販賣機同日連續投兩罐相同飲料、超商同日購買兩次相同便當、咖啡店同日連續兩杯相同咖啡、定期訂閱扣款等）。

1. **一百多萬筆資料無法人工比對**：
   當歷史交易數據累積到數十萬甚至上百萬筆時，在銀行 CSV 缺乏全域唯一交易流水號（Transaction ID）的情況下，系統與使用者根本不可能逐筆人工比對。
2. **你怎麼知道該合併還是不該合併？**
   - 若採用 `equals` 去重進行合併：系統會將上述真實發生的多次獨立消費悄悄吞掉（漏計生活支出）。
   - 若不做去重直接 append：重複匯入同一份檔案時，整份帳單所有交易金額將直接翻倍膨脹。
   唯一正解就是維持資料庫唯一性防線，直接無視或阻擋那些重複的檔案，而不是在沒有唯一識別碼的前提下自作聰明硬做合併！

### 三、方向 B（先刪後存）完全不可行：唯一使用者不打算每次都整批重來

Claude 提議的「先刪整張對帳單再重新寫入」，徹底忽視了信用卡對帳單與 NISA/年金快照的本質差異：
1. **信用卡官網歷史紀錄無法無限回溯**：
   日本各大信用卡公司（View Card、樂天、JCB、三井住友、金點卡等）的網路明細，通常僅提供過去數個月（例如 3 個月到最長 15 個月）的下載，歷史紀錄無法無限期向過去重新取得。
2. **核心商業目的：分析消費模式以推算「最低生活費」**：
   系統之所以長期累積信用卡帳單，核心目的是為了進行**長期的消費模式分析，進而推算未來的「最低生活費（Baseline Living Expense）」**。
   若每一次重新匯入都要整批刪除重建，一旦匯入的檔案是不完整的歷史檔或有缺漏，過去珍貴的歷史月份資料將永久遺失！若之後分析消費時受限於只剩下零星幾筆月份的資料，將徹底摧毀系統推算最低生活費的統計基礎。
3. **使用者意願**：
   除了手動分類會被清空之外，**系統唯一使用者明確表示：根本不打算每次都整批重來！**

### 四、方向 C（攔截例外吐訊息）脫離背景 Job 運作現實，且混淆了架構層次

Claude 提議「攔截例外並給出清楚訊息」：
1. **背景 Job 如何向前端吐訊息？**
   目前信用卡對帳單的匯入高度依賴後端背景排程 Job（`FileProcessingOrchestrator` / `JobScheduler`）自動掃描資料夾。背景批次處理檔案時，根本沒有任何前端 UI 對話框或 Toast 可以即時攔截並向使用者展示互動訊息。
2. **現狀即是 Job 運作**：
   儘管未來規劃可能會有瀏覽器擴充功能（Extension），但系統唯一使用者「現在」的日常操作就是透過背景 Job。在背景 Job 裡單純攔截例外改寫錯誤字串，並無法解決任何「補上新交易」的問題，只是無意義的表面修飾。
3. **退萬步言，就算是 Extension，問題也不在合併技巧，而是在最底層的 Model**：
   未來若真有 Extension，抓取時依舊會面臨重複抓取的狀況，屆時在前端自然可以提示「該月帳單已存在」。但問題的關鍵在於：**重複就是重複**，這根本不是在 Service 層靠「合併（Merge）」這種半吊子手法可以解決的。如果要根本解決重複與增量問題，必須從最底層的 Domain Model（例如交易唯一識別碼、生命週期定義）去徹底重構，而不是在業務邏輯層東拼西湊。
4. **現況跑得好好的，拒絕無病呻吟與過早最佳化**：
   系統唯一使用者目前日日使用背景 Job 匯入，系統**「現在跑得好好的」**，從未發生噴錯或阻礙。
   東補西補毫無意義。要補，等系統唯一使用者在實際使用時真的遇到現有信用卡帳單噴錯或卡住，再來針對真實問題修補！目前完全沒有任何修改必要。
