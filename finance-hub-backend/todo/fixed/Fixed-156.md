# [FIXED] Issue 156：DC/iDeCo對帳單合併邏輯只在「大於0才覆蓋」，使用者真實把金額歸零的情況永遠無法被正確反映，會一直沿用舊的非零數字

## 這份issue怎麼被發現的
這是這次Source Code Review針對匯入解析器的業務邏輯進行商業邏輯審查時發現的問題。

## 相關檔案
- `finance-hub/finance-hub-backend/hub-domain/src/main/java/ch/lin/finance/hub/backend/api/domain/model/accounting/dc/DefinedContributionAccountSnapshot.java:121-140`（帳戶層級`merge()`）
- `finance-hub/finance-hub-backend/hub-domain/src/main/java/ch/lin/finance/hub/backend/api/domain/model/accounting/dc/DefinedContributionFundSnapshot.java:135-154`（基金層級`merge()`）
- `finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/accounting/dc/sompo/SompoDcAllocationParserImpl.java:70-91`、`.../sompo/SompoDcStatusParserImpl.java`（兩個頁面各自只負責一部分欄位，另一部分固定填0，說明這個「大於0才覆蓋」保護機制存在的原因）

## 現狀
兩個層級的`merge()`方法，每一個數字欄位都是用`if (other.X != null && other.X > 0) { this.X = other.X; }`這種模式去覆蓋。這個設計本身是必要的——因為Sompo DC這類來源，同一天的資料是分兩個不同頁面各自匯入（例如「狀態」頁跟「配置」頁各自只提供一部分欄位，另一半固定填0去佔位），如果沒有這個「大於0才覆蓋」的保護，兩個頁面合併時，後匯入的那個頁面會直接把先匯入那個頁面的真實資料洗成0。但副作用是：這個合併邏輯從結構上就無法分辨「這個頁面本來就不負責這個欄位」跟「這個頁面確實有這個欄位、而且真實數字現在就是0」這兩種情況。

## 為何是問題
1. **帳戶層級**：使用者的雇主停止DC企業配比提繳(換工作、雇主停止配比)。下一次匯入的「配置」頁，正確解析出`monthlyEmployerContribution = 0`——但因為「大於0才覆蓋」這個保護，這個真實的0值會被忽略，資料庫裡仍然留著上個月的舊非零值，模擬引擎會持續假設雇主配比還在繼續提繳，即使現實中已經停止了。
2. **基金層級**：使用者把原本100%配置在A基金的提繳，全部轉配置到B基金。重新匯入後，A基金正確解析出`allocationPercentage=0`、`monthlyContributionAmount=0`，但因為同一個保護機制，A基金的舊配置比例/提繳金額永遠不會被清掉，模擬引擎會持續把錢投進使用者實際上已經停止投入的基金。

這兩種情境都是現實中會真實發生的事件（換工作、重新配置投資組合），不是邊緣案例，而且觸發後的結果是系統性地高估未來DC/iDeCo的成長(持續假設一筆實際上已經停止的提繳)。

## 建議修正方向
這裡列出可能的方向，不代為決定：

**方向A：讓每個解析器明確回報自己覆蓋了哪些欄位**
- 做法：解析器額外回傳「這個頁面實際涵蓋了哪些欄位」的清單，`merge()`依這份清單判斷要不要覆蓋，不要再用「值是否大於0」去反推。
- 優點：從根本解決兩種情況混在一起判斷的問題，兩個層級都能處理到。
- 缺點：需要調整每個DC/iDeCo解析器的回傳格式跟兩個`merge()`方法的介面，改動範圍中等。

**方向B：把「哪個頁面負責哪些欄位」的知識往上移到Job Service層**
- 做法：`DefinedContributionJobServiceImpl`本來就知道是哪個解析器產生了哪筆結果，可以在呼叫`merge()`時明確指定「這次要無條件覆寫哪些欄位」。
- 優點：讓`merge()`本身維持單純。
- 缺點：仍然需要同一份「頁面→欄位」對應關係，只是搬到另一個地方維護。

**方向C：維持現狀**
- 理由：如果這個系統目前兩種情境（雇主停止配比、使用者重新配置投資）都還沒真實發生過，可以先接受「停止提繳不會立刻反映、要等下一次有非零資料匯入才會重置」這個限制，記錄下來，等真的發生再處理。

Sompo DC 的網頁結構與資料呈現方式具有高度特殊性。審查者在沒有看到真實完整的網頁 HTML 結構、表單渲染與欄位缺漏情境前，僅憑後端 Java 程式碼片段就擅自推論「使用者雇主停止配比會解析出 0」、「重新配置基金會解析出 0」，完全屬於脫離真實樣本的臆測。

在缺乏真實網頁對照的情況下，任何改動都極可能在遇到真實網頁的特殊排版時產生嚴重的不可預期回歸。

### 二、資訊不對稱與後匯入洗成 0 的核心矛盾：你要怎麼解決？

Sompo DC 的業務現實是：同一個帳戶的資料**分散在不同頁面**（例如「資產狀況（Status）」頁面與「掛金配分（Allocation）」頁面）：
- **Status 頁面**：記載資產殘高、各基金持股與評價額，但**完全沒有**掛金配置資訊（`monthlyEmployerContribution` 等固定填 0）。
- **Allocation 頁面**：記載每月提繳配比與金額，但**完全沒有**資產總額與持股明細（資產殘高、單位數、評價額固定填 0）。
- 使用者匯入這兩個檔案的順序是**任意且隨機**的。

**這正是現行程式碼必須存在 `> 0` 保護的根本原因**：
- **致命場景 1**：使用者先匯入 Allocation 頁面（成功寫入每月提繳 2 萬），隨後匯入 Status 頁面。Status 頁面根本沒有配置資訊（解析出 0）。若允許 0 值覆蓋，Status 頁面一進來，**立刻把剛剛 Allocation 頁面的月提繳金額全部洗成 0**！
- **致命場景 2**：使用者先匯入 Status 頁面（成功寫入資產殘高 1,000 萬），隨後匯入 Allocation 頁面。Allocation 頁面根本沒有資產殘高資訊（解析出 0）。若允許 0 值覆蓋，Allocation 頁面一進來，**立刻把 1,000 萬資產殘高全部洗成 0**！

**請 Claude 正面回答：**
當「一個網頁有該資訊、另一個網頁完全沒有該資訊」時，後來把「沒有該資訊的網頁」丟進來時，**現存資料會被全部洗成 0 的毀滅性問題你要怎麼解決？**

### 三、請提出真正切實可行的合理解決方案
