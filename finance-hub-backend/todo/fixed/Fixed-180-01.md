# [FIXED] 180-01：房貸領域——Sony銀行房貸重新匯入時，使用者自己規劃的提前還款計劃會被整批清空；修法是`MortgageJobServiceImpl`對`earlyRepayments`補上跟另外8個使用者欄位同樣的null-fallback保護

## 跟issue-180的關係
這份文件是[issue-180](issue-180.md)（job import merge邏輯跨領域總覽）在房貸這個領域的具體案例。

## 這份issue怎麼被發現的
這是這次Source Code Review審查房貸服務層時發現的。原本審查agent提出了兩個發現：一個是「商品名稱字串比對撞名」（使用者如果有兩筆同銀行同商品名稱的房貸，匯入可能蓋錯對象），另一個是「提前還款計劃每次匯入都被清空」。前者經使用者確認後已經撤回——使用者目前只有一筆房貸、同一家銀行本來就不會核准第二筆房貸，而且這類「現實世界無法百分之百掌握的識別問題」沒有任何FP軟體會去解，系統不該為了理論上存在、但無法驗證的edge case腦補解法，判定方式跟[Fixed-157](../fixed/Fixed-157.md)處理「保單續約是否換號碼」時的立場一致。這份文件只保留後者。

## 現狀
`SaveMortgageRecordCommand`最後一個欄位是`earlyRepayments`（對應domain層的`MortgageEarlyRepayment`，使用者自己規劃「什麼時候、提前還多少、縮短年限還是減少月付」的計劃）。Sony銀行的對帳單解析器從頭到尾不會、也不可能讀到這項資訊——因為這是使用者自己在系統畫面上輸入的未來計劃，不是銀行對帳單上會記載的東西，所以解析器回傳的`SaveMortgageRecordCommand`裡這個欄位永遠是`null`。

`MortgageJobServiceImpl`合併既有資料跟這次解析結果時，對另外8個「使用者自己填的純設定值」欄位（入住日期、住宅類型等）都寫了「這次解析值若為null，就保留資料庫裡原本的值」這個保護；但`earlyRepayments`這一欄沒有同樣的保護，直接把解析器回傳的`null`原封不動放進合併後的指令裡。這個合併後的指令再交給`MortgageRecordServiceImpl.updateMortgage`處理，裡面的`applyEarlyRepayments`方法會先把房貸記錄現有的提前還款清單整個`clear()`掉，再去看這次傳進來的`request.earlyRepayments()`是不是null——因為是null，清空之後就沒有任何內容會被加回去。

`MortgageEarlyRepayment`本身早就是一張獨立的表格（透過外鍵`mortgage_record_id`關聯回`MortgageRecord`），不是跟事實欄位擠在同一張表的欄位——但這不影響這個bug的發生，因為根因不是「表結構」，是merge邏輯（`MortgageJobServiceImpl`）本身少了一個null檢查。

## 為何是問題
`earlyRepayments`這個欄位的設計意圖已經由[WONTFIX-28](../wontfix/WONTFIX-28-mortgage-early-repayment-is-forward-looking-plan-only.md)明確定案：這是使用者自己規劃「未來打算什麼時候、還多少」的計劃性安排，從頭到尾都不該、也不會由銀行對帳單提供。既然銀行對帳單結構上就不可能回報這項資訊，`earlyRepayments`在「銀行事實類欄位該被覆寫、純使用者設定類欄位該fallback保留舊值」這個判斷原則下，應該毫無疑問地歸類成後者，跟另外8個欄位用同一套null-fallback規則處理即可。

這是[issue-180](issue-180.md)「merge規則該怎麼運作」最乾淨的範例：房貸的商務ID（`bankName+contractNumber`）已經接線完成、精確比對、沒有鬆散配對的模糊地帶，`earlyRepayments`這個欄位要修的只是`MortgageJobServiceImpl`裡**漏掉的一行null檢查**，跟另外8個欄位補的保護寫法完全一樣。

## 具體錯誤情境
使用者在系統畫面上幫自己的Sony銀行房貸規劃了兩筆提前還款：2027年6月還200萬円（縮短年限）、2030年6月再還300萬円。之後因為定期更新餘額而重新匯入了這筆房貸的最新Sony銀行對帳單——匯入流程照常跑完，餘額、利率等事實類欄位正確更新，使用者畫面上回頭一看卻發現這兩筆提前還款計劃整個消失了，必須重新手動輸入一次。如果使用者沒有特別去提前還款頁面確認，很可能完全不會發現這件事發生過，直到後續的模擬結果因為少了這兩筆提前還款、現金流跟房貸餘額軌跡跟預期不一致，才會意識到有資料不見了。

## 建議修正方向
修法不涉及任何表結構變動，只需要在`MortgageJobServiceImpl`合併既有資料跟這次解析結果時，把第148行的`cmd.earlyRepayments()`改成「這次解析值若為null，就保留資料庫裡原本既有房貸記錄的`earlyRepayments`」，跟第139-147行另外8個欄位已經在用的寫法一致。這樣一來，合併後的指令傳到`MortgageRecordServiceImpl.applyEarlyRepayments`時，傳進去的就是DB現有的那份清單（不是null），`clear()`之後會立刻用這份清單整個補回去，等於這次更新對`earlyRepayments`完全沒有影響，使用者規劃的提前還款計劃維持原狀。

這是唯一合理的修法，不是多個方向中選一——跟另外8個欄位做法一致，風格統一，不需要權衡其他替代方案。

## 已解決：匯入時怎麼決定「這份對帳單對應資料庫裡哪一筆房貸」
匯入邏輯需要先回答「這份新對帳單，該去更新哪一筆既有房貸的事實欄位」這個問題，這跟`earlyRepayments`被清空是兩個獨立的子問題，已經有解。

原本的審查發現提案是「用商品名稱字串比對，但使用者如果有兩筆同名房貸就會撞名蓋錯對象」，使用者否決了這個方向，理由是：
1. 使用者目前只有一筆房貸、而且同一家銀行本來就不會核准第二筆房貸給同一個人，這個情境在使用者自己的真實使用情境裡不存在。
2. 更根本的問題是，這類「現實世界的識別問題」本質上無解——同樣名稱但單號不同可能是續約後的新產品、同樣名稱單號相同但實際是不同商品、不同名稱但只是商品改了名字，這些情況光靠程式邏輯猜測都無法保證正確，除非能讓現實世界的銀行系統全部遵照這個FP模擬工具的需求來設計識別碼，否則任何猜測式的比對邏輯都只是在特定情境下恰好矇對、在其他情境下反而製造新的錯誤覆蓋風險。

**後續進展**：使用者已經在`MortgageRecord`新增`bankName`、`contractNumber`兩個欄位，並把`@EqualsAndHashCode(of = { "bankName", "contractNumber" })`設成這個entity的相等性判斷依據；`MortgageJobServiceImpl`的匯入比對邏輯也已經改用這組組合取代原本的`loanName`字串比對。查證確認：`contractNumber`是真的從Sony銀行頁面「契約番号」解析出來的事實欄位，`bankName`則是parser寫死的常數（代表「這支parser對應哪家銀行」，不是從頁面解析）。這組商務ID目前只在資料庫層用程式碼null檢查防守（任一欄位為null時跳過比對、走新增分支），沒有資料庫層級的唯一性約束——要不要補上，留給使用者決定，不影響這組商務ID本身已經可以使用的結論。這組商務ID的用途是「job import merge時用來在DB裡定位既有那一筆房貸」。
