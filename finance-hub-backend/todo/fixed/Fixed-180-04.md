## 現狀
SBI、Sompo兩家公司各自都有三種頁面（會員資料頁、配分頁、資產現狀頁），對應到6支parser實作。這三種頁面不是「同一份資料的三個不同版本」，是「同一個帳戶快照的三個不同切面」——每個頁面只填自己負責的那部分欄位，其餘欄位固定填0（或對於`enrollmentDate`這類非數值欄位固定不設）：

| 頁面 | 填的欄位 | 固定0/不填的欄位 |
|---|---|---|
| 會員資料頁 | `enrollmentDate` | `totalAssetValue`、`totalAccumulatedContribution`、`monthlyEmployerContribution`、`monthlySubscriberContribution`、`monthlyTotalContribution`全部填0 |
| 配分頁 | `monthlySubscriberContribution`/`monthlyTotalContribution`；底下`DefinedContributionFundSnapshot`的`monthlyContributionAmount`/`allocationPercentage` | `totalAssetValue`、`totalAccumulatedContribution`固定0；fund層級的`units`/`averageCost`/`currentPrice`/`totalPrincipal`/`currentMarketValue`/`unrealizedGainLoss`固定0 |
| 資產現狀頁 | `totalAssetValue`/`totalAccumulatedContribution`；底下fund的`units`/`currentPrice`/`totalPrincipal`/`currentMarketValue`/`unrealizedGainLoss` | `monthlyEmployerContribution`/`monthlySubscriberContribution`/`monthlyTotalContribution`固定0；fund層級的`monthlyContributionAmount`/`allocationPercentage`固定0 |

`DefinedContributionJobServiceImpl.parseFileWithAllParsers`依序呼叫每個parser的`canParse`，第一個回傳true的就用它解析，但選完之後完全不保留「這次選到的是三種頁面裡的哪一種」這個資訊——parser介面（`DefinedContributionParser`）本身也沒有任何方法可以回報這件事。

因為Service層不知道「這份快照的事實內容是哪個頁面提供的」，`DefinedContributionAccountSnapshot.merge()`跟`DefinedContributionFundSnapshot.merge()`只能改用猜：`if (other.totalAssetValue != null && other.totalAssetValue > 0)`才覆蓋、`if ((other.allocationPercentage != null && other.allocationPercentage > 0) || (other.monthlyContributionAmount != null && other.monthlyContributionAmount > 0))`才覆蓋——用「這個值是不是大於0」當作「這次有沒有填這個欄位」的替代判斷。

## 為何是問題
0在DC/iDeCo這個領域是合法的真實業務值，不是「這個頁面沒有提供這項資訊」的代號——這兩件事目前被`merge()`裡的`> 0`判斷混為一談：
- 剛加入iDeCo、還沒有任何提繳記錄的新帳戶，`totalAssetValue`、`totalAccumulatedContribution`真實地是0。
- 如果使用者某個月請假或公司停止提繳，導致`monthlyEmployerContribution`真實地變成0，這是一筆**真實發生的事實**；但`merge()`的`other.monthlyEmployerContribution > 0`判斷會把這次解析出來的0當成「這個頁面沒有填」而拒絕覆蓋，繼續沿用資料庫裡上個月的非零舊值。模擬引擎會因此繼續把一筆實際上已經停止的提繳金額算進未來的現金流推估，而且不會有任何警訊，因為資料庫裡的數字看起來「正常」（非零），只是不是真的。

這三個頁面目前能用`> 0`判斷矇混過關，純粹是因為這三支parser剛好都選擇用0去表示「這個頁面沒有這項資訊」——這是解析器實作上的巧合，不是一個可靠、經得起未來變化考驗的規則。**根因不是忘記寫某一行防呆，是merge邏輯本身建立在一個錯誤的假設上：試圖讓domain層光靠看一個數值，去反推「這份資料實際上代表什麼意思（這是頁面沒填，還是真的是0）」——這件事domain層本來就無法僅憑數值本身準確判斷，因為同一個數值（0）在不同情境下的意義完全相反。**

這個問題曾經被嘗試修正過四次，每次修正都被使用者用`git`回退——使用者指出失敗模式是：改法會不知不覺地從「用`> 0`判斷」換成「用`!= null`判斷」，但這兩種寫法是同一個錯誤的不同外觀，domain層依然是靠觀察這次傳進來的值本身去猜測「這個欄位這次是不是真的被填了」，不是真正知道「這份資料來自哪個頁面」。只要domain層的判斷邏輯還停留在「看這個欄位的值長什麼樣子來決定要不要覆蓋」，不管判斷條件寫成`> 0`還是`!= null`還是其他任何數值相關的條件，都只是換了一種方式繼續猜，沒有解決根本問題。

## 具體錯誤情境
使用者的企業型DC帳戶，公司每月提繳3萬円（`monthlyEmployerContribution=30000`）。某個月使用者離職、公司停止提繳，使用者重新匯入Sompo的配分頁最新存檔，這次頁面上顯示提繳金額變成0（因為已經沒有雇主提繳了）。`merge()`收到這筆`monthlyEmployerContribution=0`的新資料時，因為`0 > 0`不成立，判斷為「這次沒有填這個欄位」，拒絕覆蓋，資料庫裡繼續保留舊的30000。之後的模擬結果，會持續把這筆實際上已經停止的3萬円月提繳算進退休資產累積推估，直到使用者自己發現模擬結果跟實際狀況不符，才會意識到這筆錢已經不會再進帳。

## 建議修正方向
正確方向是讓Service層明確知道「這份解析結果來自三種頁面裡的哪一種」，依此分派到三個各自只負責自己那部分欄位的merge方法，domain層完全不用任何數值判斷去猜測，一律無條件接受它被要求覆蓋的那些欄位：

1. **新增一個頁面類型的enum**（例如`DefinedContributionPageType { MEMBER_INFO, ALLOCATION, STATUS }`），跟現有的`DefinedContributionType`（`IDECO`/`CORPORATE_DC`，代表公司/制度類型，是完全不同的分類維度）區分清楚，不要混用或擴充同一個enum。
2. **`DefinedContributionParser`介面新增一個方法**，讓每一支parser回報自己對應的頁面類型（例如`DefinedContributionPageType getPageType()`）。6支現有parser實作各自回報對應的值：`SbiIdecoMemberInfoParserImpl`/`SompoDcMemberInfoParserImpl`回報`MEMBER_INFO`，`SbiIdecoAllocationParserImpl`/`SompoDcAllocationParserImpl`回報`ALLOCATION`，`SbiIdecoStatusParserImpl`/`SompoDcStatusParserImpl`回報`STATUS`。
3. **`DefinedContributionJobServiceImpl.parseFileWithAllParsers`**在選中某支parser後，連同解析結果一起把這支parser的頁面類型往下傳（可以包成一個小的結果物件，或是額外回傳一個值，不只回傳`DefinedContributionAccountSnapshot`本身）。
4. **`DefinedContributionAccountSnapshot`新增三個分開的方法**：`mergeMemberInfoFacts(DefinedContributionAccountSnapshot incoming)`（只覆蓋`enrollmentDate`）、`mergeAllocationFacts(...)`（只覆蓋`monthlySubscriberContribution`/`monthlyTotalContribution`，以及底下fund的`monthlyContributionAmount`/`allocationPercentage`）、`mergeStatusFacts(...)`（只覆蓋`totalAssetValue`/`totalAccumulatedContribution`，以及底下fund的`units`/`averageCost`/`currentPrice`/`totalPrincipal`/`currentMarketValue`/`unrealizedGainLoss`）。這三個方法內部都是無條件直接賦值（`this.xxx = incoming.getXxx()`），不做任何`> 0`或`!= null`的條件判斷——因為呼叫到哪一個方法本身，就已經是「這個欄位這次確實有事實」的保證，不需要再用數值去二次確認。
5. **`DefinedContributionJobServiceImpl`依照頁面類型呼叫對應的方法**：`switch (pageType) { case MEMBER_INFO -> existing.mergeMemberInfoFacts(incoming); case ALLOCATION -> existing.mergeAllocationFacts(incoming); case STATUS -> existing.mergeStatusFacts(incoming); }`。

`monthlyEmployerContribution`目前查證下來沒有任何一支parser會填入非零值（6支parser的原始碼裡都是固定傳`0L`），如果這個欄位實際上也該歸屬於某個頁面（例如企業型DC的某個官方頁面可能會顯示雇主提繳金額，但目前查無對應parser），需要使用者確認這個欄位目前的設計意圖，這份issue不代為判斷；如果現有頁面確實都不提供這項資訊，這個欄位目前只能透過使用者畫面手動輸入維護，不受這次merge邏輯重構影響。

## 第二個缺口：fund層級完全沒有商務ID，用`fundName`字串比對找既有fund，風險會跟帳戶層級的問題疊加
這是跟上面帳戶層級問題同時存在、根因相同（domain層/比對邏輯試圖從資料本身反推一件它本來就無法單憑資料本身確定的事），但影響範圍不同的另一個缺口，歸在這份issue一起處理。

**現狀**：查證確認`DefinedContributionFundSnapshot`這個domain實體上，除了資料庫自增主鍵（`fundId`，`DefinedContributionServiceImpl.updateAllocation`用`findById(fundId)`查詢）之外，**完全沒有任何商務層級的識別欄位**（沒有基金代碼、沒有任何類似NISA領域`fundCode`那種從頁面`href`屬性解析出來的穩定代碼）。`DefinedContributionAccountSnapshot.merge()`第144行目前用`f.getFundName().equals(otherFund.getFundName())`——基金名稱字串完全相等——去判斷「這是不是同一支基金」。查證確認四支負責fund層級資料的parser（`SbiIdecoAllocationParserImpl`、`SbiIdecoStatusParserImpl`、`SompoDcAllocationParserImpl`、`SompoDcStatusParserImpl`）都沒有解析任何類似href代碼的邏輯，目前網頁上有沒有類似NISA那種可以抓的代碼，沒有真實網頁樣本可以確認，不能在這裡腦補斷言「網頁上沒有」或「網頁上有」。

**為何是問題**：這跟[issue-181](issue-181.md)NISA領域已經記錄的`fundName`不穩定問題是同一種風險——基金名稱是人類可讀字串，天生比代碼更容易在不同時間點的解析結果之間出現細微差異（空格、半角全角、發行公司改字用詞）。只要這次解析出來的`fundName`跟DB裡既有那一筆存的字串不完全相等，就會被誤判成全新的fund而重複新增，而不是既有fund的更新；更關鍵的是，這個風險會跟上面帳戶層級的問題直接疊加——不管帳戶層級的頁面分派架構修得多正確，只要fund層級的比對鍵本身不穩定，`mergeAllocationFacts`/`mergeStatusFacts`呼叫到的都可能是「誤判出來的那一筆」，不是真正該更新的那一筆，等於上層架構修好了，下層還是會錯。

**建議修正方向**：
1. **先查證真實網頁，確認SBI、Sompo的配分頁/資產現狀頁上，基金這一層有沒有任何形式的穩定代碼可以抓**（例如連結的`href`、表格儲存格的`data-`屬性、或任何不隨名稱顯示方式變動的識別碼）——這點需要使用者或有真實樣本的人去確認，這份issue不能在沒有樣本的情況下猜測網頁結構。
2. **如果查到有穩定代碼**：比照NISA領域`fundCode`的做法，新增對應欄位、parser解析、`DefinedContributionFundSnapshot`的比對鍵改用這個代碼，不用`fundName`。
3. **如果查證後確認網頁上真的沒有任何代碼可用**：退回`fundName`字串比對是目前唯一可行的方式，但要接受跟NISA領域同樣程度的誤判風險；這個決定需要使用者明確承認並接受這個限制，不是因為沒去查就預設走這條路。
4. 不管哪種情況，fund層級的比對鍵要怎麼接線，都應該放在帳戶層級的頁面分派架構（見上方第1-5點）確定之後才動手，因為`mergeAllocationFacts`/`mergeStatusFacts`內部呼叫fund層級比對的時機，取決於帳戶層級分派邏輯先確定下來的呼叫介面長什麼樣子。

**建議修正方向（已查證更新）**：
1. **真實樣本查證結論**：使用者已提供真實 HTML 樣本（`SBIベネフィット・システムズ -  ホーム.html` 與 `SBIベネフィット・システムズ - 資産状況.html`），查證確認商品詳細連結 `subSyohinNew('../Knowledge/JP_D_Knowledge_InvestTrust_Inquiry.aspx?...scd=9200181027')` 中的 `scd` 參數在配分頁（小寫 `scd`）與資產狀況頁（大寫 `SCD`）完全相同，是 SBI 跨頁面穩定的專屬商品代碼（商品コード）。
2. **新增欄位與解析**：在 `DefinedContributionFundSnapshot` 新增 `fundCode`（比照 NISA 領域命名）；由 SBI 的配分與資產現狀 Parser 解析提取 `scd` 賦值。
3. **商務代碼唯一比對策略（嚴格以 `fundCode` 為準，徹底廢除 `fundName` fallback）**：比對既有基金時，**100% 嚴格以 `fundCode` 為唯一比對鍵**。廢除以 `fundName` 作為 fallback 的做法，避免使用者在不同機構/帳戶投資同名商品時因名稱相同而引發跨機構誤配的嚴重商務 bug。既然雙方機構均能解析出 `scd`，商務識別應完全依賴此唯一代碼。
4. 既然 SBI 代碼已確認，將此改動直接融入下方分階段規劃中，依 Java 相依關係從底層欄位開始循序推進。

## 分階段重構規劃（保持 Context Window 專注與可追蹤）

為了避免單次改動範圍過大、跨越過多層級導致遺漏或 context 過載，依據依賴單向性與上述架構決策拆分為以下執行階段：

### 第一階段：Domain 欄位底座 + PageType 定義（底座就位）
- **目標**：在底層模型補齊 `fundCode` 欄位與頁面切面類型，為後續 Parser 與 Service 提供型別安全的依賴基礎。
- **改動範圍**：
  1. `DefinedContributionFundSnapshot`：
     - 新增欄位 `private String fundCode;`（含 getter/setter/建構子相容擴充）。
  2. 新增 enum `DefinedContributionPageType { MEMBER_INFO, ALLOCATION, STATUS }`（注意：與制度類型 `DefinedContributionType` 嚴格區分）。
  3. 在 `DefinedContributionParser` 介面新增方法 `DefinedContributionPageType getPageType()`。
- **驗證方式**：執行 `mvn compile`，確保底層模型與介面宣告無編譯錯誤，現有業務邏輯零破壞。

### 第二階段：Parser 實作切面宣告 + SBI 與 Sompo 解析 `fundCode`
- **目標**：讓 6 支 Parser 明確回報其切面類型，並讓 SBI 與 Sompo 的四支 Fund Parser 在解析時自動帶出穩定的 `fundCode`（Benefit Systems 共通架構之 `scd`）。同時移除 `DefinedContributionFundSnapshot` 舊有無 code 建構子，確保商務唯一識別碼非空。
- **改動範圍**：
  1. `DefinedContributionFundSnapshot`：
     - 將 `fundCode` 標記為 `@NotNull` 與 `nullable = false`。
     - 移除舊的不含 `fundCode` 建構子，強制基金快照必須具備商務代碼。
  2. 6 支 Parser 實作補上 `getPageType()`：
     - `SbiIdecoMemberInfoParserImpl` -> `MEMBER_INFO`
     - `SompoDcMemberInfoParserImpl` -> `MEMBER_INFO`
