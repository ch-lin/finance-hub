# [FIXED] Question 160：同一張Amazon訂單如果同時用了「禮品卡」跟「育兒支援券」兩種抵用方式，後解析到的會蓋掉先解析到的——需要先確認這種同時使用的情境是否真的會發生

## 這份question怎麼被發現的
這是這次Source Code Review針對Amazon訂單解析業務邏輯進行審查時發現的問題。核心機制(覆蓋而非累加)可以從程式碼100%確認，但「同一張訂單是否真的會同時出現兩種抵用方式」這個觸發條件，無法只靠讀程式碼確認。


- 對照：同檔案第299行，`discounts`欄位用的是累加寫法(`order.setDiscounts(現有值.add(新金額))`)，跟`giftCardAmount`的覆蓋寫法不一致
- 對照：[Fixed-100](../fixed/Fixed-100.md)/[Fixed-100-01](../fixed/Fixed-100-01%20修正%20Amazon%20育兒支援券折抵漏算問題.md)——這份已結案的修正，把「育兒支援券」併入「禮品卡」這同一個欄位處理；當初那份修正的測試案例本身，就因為這個覆蓋邏輯，把預期值從4改成10（後解析到的「育兒支援券(-10)」蓋掉了先解析到的「禮品卡(-4)」），但這個現象當時只被當作「調整測試預期值」處理，沒有被進一步當作一個可能影響真實訂單的產品情境去討論。

## 現狀（不涉及爭議的部分，純粹讀程式碼得到的事實）
`giftCardAmount`這個欄位是直接覆蓋寫入，不是累加。如果同一張訂單的結算明細裡，同時出現「禮品卡」跟「育兒支援券」兩行各自獨立的抵用金額，兩者中只有後解析到的那一行金額會留在`giftCardAmount`裡，前一行的金額會被整個蓋掉——不只是顯示上看不到，連`getTotalDeductions()`(用於報表「總共省下多少錢」的計算)跟`verifyOrderMath`(核對訂單金額是否正確、決定是否要標記為`needsReview`)都會用到這個被蓋掉後、缺少一塊的金額，可能讓一筆原本正常的訂單被誤判成金額對不起來、需要人工複核。

## 不確定、需要查證才能回答的地方
這個情境需要同一張訂單的結算明細裡「同時」出現禮品卡跟育兒支援券兩種各自獨立的抵用金額行——這在Amazon實際的結算頁面上是否真的會同時出現，這次審查沒有實際的雙欄位HTML樣本可以確認，純粹是從程式碼邏輯推論出「如果發生會怎樣」，不代表確定會發生。

## 需要查證的問題
使用者本人的真實Amazon訂單中，是否曾經出現過同一張訂單同時用禮品卡餘額+育兒支援券付款的情況？如果從未發生過，這份question可以先維持現狀；如果確實發生過(或未來可能發生)，則需要處理這個覆蓋問題。

## 不建議的處理方式
不建議在沒有實際樣本驗證「兩者是否真的會同時出現」之前，就貿然把`giftCardAmount`改成累加寫法——如果Amazon的真實頁面偶爾會把同一筆禮品卡金額重複列成兩行(目前無法排除這個可能性)，改成累加反而會變成重複計算，從一種風險換成另一種風險。這也是當初[Fixed-100](../fixed/Fixed-100.md)選擇把育兒支援券併入禮品卡欄位、而不是給它一個獨立欄位時，已經權衡過的方向，重新打開這個決定需要更明確的真實情境佐證。

## 查證結果與事實確認（真實使用者數據）
- **真實使用情境**：使用者本人確認，在真實 Amazon 購物歷史中，**確實曾經發生過**同一張訂單同時使用「一般禮品卡餘額」與「育兒支援券」抵用付款的情形。
- **Amazon 網頁收據之真實表現**：但在 Amazon 最終產生的訂單明細與收據（領収書）網頁中，**一律將「育兒支援券」合併顯示在「Amazonギフトカード」（禮品卡）單一欄位中**，收據上從未分開列出「ギフトカード」與「育児支援券」兩行各自獨立的金額。
- **業務機制與底層原因**：兩者在 Amazon 系統架構中本質上都是帳戶內的儲值點數（Stored-value balances/points），「育兒支援券」實質上即為限定適用商品範圍的 Amazon ギフト券。在出帳時，Amazon 系統端直接將其併入禮品卡折抵總額，因此前端明細本來就不存在拆分。

## 針對審查質疑的回應與技術定論
1. **「雙欄位先後覆蓋導致金額短少」為脫離真實平台規格的純程式碼臆測（False Positive）**：
   - 既然真實 Amazon 網頁永遠只會輸出一行合併後的禮品卡折抵金額，在迴圈解析時就**只會命中一次**，物理上**絕不會發生**「網頁同時有兩行、後者蓋掉前者導致漏算折抵」的狀況。
2. **下游解析器無法逆向捏造上游未提供的資料**：
   - 既然 Amazon 網頁收據上已經在服務端將兩者合併為單一數額，身為第三方下游的 HTML 解析器，**不可能也不應該無中生有地憑空拆解**個別扣款數字（除非審查人能聯絡 Amazon 產品經理命令他們修改網頁規格拆行顯示，否則要求解析器拆分是不切實際的幻想）。
3. **現行實作是兼顧相容性與正確性的最佳 SSOT 設計**：
   - 判斷式包含「Amazonギフトカード」、「Amazon商品券」、「ギフトカード」與「育児支援券」，確保無論 Amazon 在特定介面以何種文字標註該行折抵，皆能精準擷取。
   - `order.setGiftCardAmount(amount.abs())` 記錄了該次結算的真實折抵總額，讓 `verifyOrderMath()` 的核對公式（`商品合計 - 折抵 = 實付`）完全吻合，不會引發誤判或假警報。
   - 正如本文件先前所述，若貿然改為累加，反而會帶來重複計費的巨大風險。
4. **單元測試覆蓋現象之原由釐清**：
   - [Fixed-100](../fixed/Fixed-100.md) 當初測試預期值由 4 改為 10，純粹是因為 `AmazonOrderParserImplEdgeTest#testParseOrderSummaryBranchCoverage` 是一個人造的「分支覆蓋測試」，刻意在一份 Dummy HTML 裡把所有可能的關鍵字 row 串在一起測覆蓋率所產生的副作用，並非真實 Amazon 訂單格式。

## 結論與處置
- **處置**：**維持現狀，直接結案（Closed - By Design / Invalid Issue）**。
- **行動**：無需修改任何業務程式碼，現行設計完全符合真實 Amazon 平台規格與會計核算邏輯。
