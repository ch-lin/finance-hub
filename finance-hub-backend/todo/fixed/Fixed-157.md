# [FIXED] Question 157：保單續約如果換發新的保單號碼，重新匯入時的比對方式可能會讓舊保單變成孤兒紀錄、永遠不會到期——需要先確認續約是否真的會換號碼

## 這份question怎麼被發現的
這是這次Source Code Review針對匯入解析器的業務邏輯進行商業邏輯審查時發現的問題，但其中一個關鍵事實（續約是否換發新保單號碼）無法只靠讀程式碼確認，需要使用者對real-world保單續約流程的了解。

## 相關檔案
- `finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/accounting/insurance/InsuranceJobServiceImpl.java:140-157`（重新匯入時，比對既有保單的方式是用`policyName`完全相同去配對）
- `finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/accounting/insurance/parser/SonyAssuranceFireHtmlParser.java:92`、`.../SonyLifeSummaryHtmlParser.java`、`.../SonyLifeDetailHtmlParser.java`（解析器都是用`保單名稱 + " (" + 保單號碼 + ")"`這種格式去組成`policyName`）
- 對照：[WONTFIX-06](../wontfix/WONTFIX-06.md)（這份文件裡使用者自己提到保單續約是「重新簽一份全新合約」）

## 現狀（不涉及爭議的部分，純粹讀程式碼得到的事實）
重新匯入時用來判斷「這是不是同一張保單」的字串，裡面包含了解析出來的保單號碼。兩個保單解析器都固定把`endDate`設為null——而`endDate`為null在這個系統裡代表「沒有到期日、視為永久有效」（出自WONTFIX-06的查證結果）。

## 不確定、需要使用者確認才能回答的地方
如果日本的地震保險/人壽保險，續約時確實會換發一組新的保單號碼（WONTFIX-06裡使用者自己的說法是「重新簽一份全新合約」，這點強烈暗示會換號碼，但這份文件並沒有明確、直接地確認這一點），那麼重新匯入續約後的保單時，因為`policyName`字串裡包含了舊的保單號碼，新保單不會被判定成「同一張」，而是會被當成一張全新的保單插入資料庫。原本那張舊保單的紀錄，因為`endDate`永遠是null，不會停止被計入保費支出或稅務扣除——這代表模擬引擎會同時把舊保單(應該已經失效)跟新保單(真正有效)的保費都算進去，變成重複計算一份概念上連續的保障。

## 需要查證的問題
1. 使用者實際續約Sony Assurance/Sony Life的保單時，新合約的保單號碼是否確實跟舊合約不同？
2. 如果答案是「會換號碼」，這份question就會變成一個真正的issue，需要處理；如果答案是「保單號碼續約後維持不變」，這份question就可以直接結案，不需要任何修正。

## 不建議的處理方式
不建議在沒有確認「續約是否換號碼」這個事實之前，就直接假設它會換號碼並據此修改比對邏輯——如果實際上號碼續約後維持不變，調整比對邏輯反而可能在真正需要分辨「同時持有多張同類型保單」的情境下，把兩張本來獨立的保單誤判成同一張。

## Product Manager（使用者）回饋與架構質疑（2026-10-12）

### 一、事實查證與現狀落實成果
1. **火災保險附帶之地震保險（Sony 損保）**：
   - 經查證，續約時**不會換發新單號**（沿用原保單號碼）。
   - 主約期間（10 年）與滿期日（`2031-04-01`）已實裝自動解析，保單在時間軸上有明確邊界，自然終止。
2. **自動車保險（Sony 損保）**：
   - 續約時**會換發新單號**（重新簽訂一份全新合約）。
   - 但自動車保險本為 1 年期定期契約，Parser 已實裝解析滿期日（如 `2027-06-17`）。舊合約到期後時間軸自然交接終止，**根本不存在「舊約無限期生效變成孤兒保單」的問題**。
3. **人壽保險（Sony 生命）**：
   - 終身壽險本質上終身有效無到期日；定期人身保險（如家族收入保險）的滿期日亦已於 Detail 頁面實裝解析（`2049-08-31`），時間軸同樣已補齊。

### 二、針對 Claude「孤兒保單質疑」的前提盲區與反質問

Claude 原本的質疑邏輯是：「保單續約若換單號，舊單因為 `endDate == null` 會變成孤兒保單永遠重複扣款，因此系統必須想辦法自動處理」。但這個質疑前提忽略了現實世界的真實限制：

1. **若來源網頁/合約本質上就沒有到期日，系統如何憑空捏造 `endDate`？**
   - 終身壽險本質就無到期日；或是某些保險公司的簡易照會網頁根本未提供滿期日。
   - 在客觀資料源本就沒有到期日的情況下，系統將 `endDate` 設為 `null` 是唯一客觀正確的做法。
   - Claude 既然認為「換了不同單號就必須要有 `endDate`」，那在來源網頁根本沒有到期日的時候，系統要如何「捏造」出合理又有效的 `endDate`？請提出合理、合法且合乎現實的具體解決方式。
2. **系統若擅自「猜測並刪除/失效舊單」，法律責任誰負？**
   - 若不靠到期日，而是主張由系統在匯入新單時「自動把舊單標記為失效或刪除」：請問系統要如何明確界定「沒有 `endDate` 的單」哪一張該刪、哪一張不該刪？
   - 難道同性質的單只要匯入新約，系統就武斷把舊約刪了？
   - 現實中使用者完全可能同時持有多張同性質合約（例如同時買兩間不同公司的壽險）。系統不是神，若因為同性質就任意猜測誤刪使用者的真實有效合約，造成理賠規劃或資產模擬失真，法律責任誰承擔？提出質疑的 Claude 要負責承擔嗎？
