# [FIXED] Issue 152-01：DC/iDeCo年資覆寫設定的「悄悄多算一年」問題，只修好了「有既有快照」這一半，「沒有快照、只靠設定值試算」的另一半仍然是原來的錯誤邏輯

## 這份文件怎麼來的

## 現狀
Issue-152當初選定的修正方向，是「覆寫值不要經過日期轉換，直接鎖定這個整數」。這個方向在「使用者名下已經有既有DC/iDeCo快照」這個分支確實被正確採用了——程式碼直接把使用者輸入的整數存進`contributionYears`，完全不去合成`LocalDate.now().minusYears(N)`這種假日期。

但同一個檔案裡還有另外兩個分支，分別對應「使用者名下沒有任何既有快照，只是在設定頁勾選了『每月DC配比提繳金額』/『每月iDeCo提繳金額』、系統因此虛擬出一個基金去代表這筆提繳」的情境——這兩個分支完全沒有被這次修正碰到，依然原封不動保留著issue-152當初要修掉的那段邏輯。

## 為何還是問題
`YearlySimulationPipeline`裡判斷「要不要每年重新計算年資」的依據，是「這個帳戶的入職日欄位是不是null」，不是「這個帳戶有沒有既有快照」。只要`dcEnrollmentDate`/`idecoEnrollmentDate`不是null（而這兩個沒修到的分支依然會把它設成一個非null的假日期），每一年只要還有實際提繳，`YearlySimulationPipeline`就會重新呼叫`TaxDateUtils.calculateTaxServiceYears`去跟當年12月31日比對——這正是issue-152原本指出的「含頭含尾進位，套在剛好整年差距的合成日期上會多算一年」那個機制，一模一樣地重新發生。

具體情境：使用者沒有匯入過任何DC/iDeCo對帳單，只是在設定頁填了「每月iDeCo提繳3萬円」，並開啟「年資覆寫=3年」。因為沒有既有快照，程式碼走進沒有被修正到的那個分支：合成日期`今天(2026-10-13).minusYears(3)` = `2023-10-13`，存進`idecoEnrollmentDate`。模擬第一年，`YearlySimulationPipeline`讀到這個非null日期，重新呼叫`calculateTaxServiceYears(2023-10-13, 2026-12-31)`——這段期間是3年2個月18天，進位後變成4，不是使用者原本輸入的3。而且因為這個合成日期會一直留在`idecoEnrollmentDate`裡，之後每一年只要還有提繳，都會重新用這個越來越偏移的假日期去跟當年12月31日比對——跟issue-152原本描述的「只在第一年多算一年、之後固定維持」不同，這個沒修到的分支反而會隨著模擬年數增加持續惡化，不會穩定在+1。

## 建議修正方向
Issue-152當初選定的方向本身是對的，只是需要把同一個精神套用到這兩個目前還沒改到的地方，不需要重新評估方向：

**做法：把這兩個沒修到的分支，改成跟已經修正好的「有快照」分支一樣的寫法**
- 第98行：拿掉`context.setDcEnrollmentDate(LocalDate.now().minusYears(overrideVal));`這一行，改成直接`context.setDcContributionYears(overrideVal);`，不要再動`dcEnrollmentDate`（讓它維持null）。
- 第170行：同樣的改法套用在iDeCo那一側。
- 這樣改完之後，`YearlySimulationPipeline`裡原本就存在的`else if (annualContribution > 0) { setContributionYears(getContributionYears() + 1); }`邏輯會自然接手每年遞增，跟「有快照」分支現在的行為完全一致，不需要額外新增任何邏輯分支。
