# Fixed 83：NISA帳戶類型辨識失敗預設「成長投資枠」，Javadoc只論證了終身額度面向的保守性，年度上限面向沒說清楚

## 判定：只採用方向A，且Javadoc要「補完整」而非刪除（2026-09-15）
**理由**：使用者指出，糾結「辨識失敗時哪一種預設值才算保守」本身是文字遊戲——消費類支出的模擬本來就該偏保守，但投資類的模擬目標剛好相反：是要在報酬最大化的前提下，盡量把資金有效部署，才能算出生活現金真正的可用空間。原本的方向B、C都是基於「一定要選出一個各面向都保守的預設值」這個前提去設計的，這個前提本身就是我過度解讀，撤回。

使用者另外指出：依她觀察，Gemini編輯程式碼時常會順手刪掉一般註解，但`/** ... */`這種Javadoc區塊註解不會主動被刪掉——這段本來就是Javadoc，屬於不會被順手清掉的類型。既然不會被清掉，真正該決定的問題只剩下：這段說明是否重要到「值得寫完整」，還是LLM看程式碼本身就能正確判斷、寫不寫都無所謂。這個判斷交給我（背後也是LLM）決定。

**決定：這段邏輯值得寫完整，不是可以拿掉的那種。** 理由很直接——這整個Fixed-83的起點，就是我自己（一個LLM）看到「預設值是保守設計」這段不完整的Javadoc，加上程式碼本身（`parse()` 的邏輯、`TaxConstants` 裡的兩組上限數字），並沒有因此推導出正確的全貌，反而誤判成一個bug。這正好證明了：光看程式碼、不靠完整註解，並不足以讓LLM正確理解「保守」在這裡其實是雙面的（終身額度面向保守，年度上限面向反而寬鬆）。所以這段說明屬於「重要、且沒有人類工程師會看」的類型，應該寫完整。

## 現狀
`NisaAccountType.parse()` 辨識失敗時，一律預設回傳「成長投資枠」（GROWTH）。程式碼上方的Javadoc註解，說明選擇這個預設值是刻意的「保守」設計，但只從終身額度子上限（成長投資枠自己的1200萬元子上限比較小）這一個面向去論證，沒有提到年度上限面向（成長投資枠240萬／年，是定期定額枠120萬／年的兩倍）其實是相反的效果——如果只看年度上限，GROWTH其實是比較寬鬆、不是比較保守的選項。

## 建議修正
**方向A（採用）：維持預設GROWTH，修正Javadoc註解，誠實說明這個預設值在年度上限面向其實是比較寬鬆、只有在終身額度面向才是比較保守，兩個面向本來就會拉出不同的答案，不是單一「保守」兩個字可以一句話概括的**
- 零邏輯風險，不改動任何計算行為，只是讓文件更準確。
