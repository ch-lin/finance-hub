# Reply to FINDING-12-01's "Resolution (Implemented)" — verified against live source (backend + frontend)

## Verdict: REGRESSION_INTRODUCED — the core seed+increment arithmetic is genuinely correct, but the feature's own headline deliverable (the manual override "escape hatch") is unreachable from the UI

**Revision note (post-review design discussion with the author, superseding how the HIGH finding below was originally framed):** reverting `contributionYears` to 0 when a balance-only resync omits the Member Info page is **not itself a bug**. For a retirement-solvency simulation, understating years (and therefore the tax deduction, and therefore projected assets) is the safe-side error — the alternative of carrying forward a possibly-stale value risks the simulation showing solvency when the real outcome is insolvency, which is the worse failure mode. No "carry forward last known value" or automatic conflict-resolution logic should be built for this. The real gaps are (a) the override escape hatch being unreachable (CRITICAL, below) and (b) no UI signal that a given contribution-years value is an unconfirmed fallback rather than a value backed by real captured data — see revised HIGH section.

## Note on discovery
This reply covers a much larger surface than Fixed-11-01 alone: per the request, this also reviews the DDD refactor that accompanied the fix (domain fields pulled out of `UserProfile` into three new dedicated settings verticals — DC, NISA, Salary — each with its own controller/DTO/command/result/mapper/service). Per your explicit instructions, request-validation completeness and the BFF-vs-tabbed-UI question are **out of scope** and not discussed below. Everything here is either a business-logic correctness issue or an implementation bug in what was actually changed.

Verified via an 11-agent workflow: 1 map/locate pass, 5 parallel deep-verification passes (parsers, tax-math arithmetic, backend controller/service wiring, frontend wiring, migration/regression sweep), and 4 adversarial skeptics (2 independently re-deriving the tax-math arithmetic from the live files, 2 independently re-deriving the migration-completeness claim). **All 4 skeptics refuted** the claims they were assigned to attack, after re-reading the live source themselves rather than trusting the prior agents' reports — the findings below are corroborated at least twice, from scratch, in every case.

## What's actually correct (confirmed, not just claimed)
- `enrollmentDate` extraction targets `資格取得年月日` (qualification date), not `申込年月日` (application date) — the legally distinct field Fixed-11-01 specifically called out. Correct in both `SompoDcMemberInfoParserImpl.java` and `SbiIdecoMemberInfoParserImpl.java`.
- Floor behavior: `Period.between(enrollmentDate, LocalDate.now()).getYears()` truncates toward zero, which is arithmetically equivalent to `floor()` for a non-negative past-to-now span — matches Fixed-11-01's recommendation exactly.
- Override-replaces-computed (not additive) — confirmed via `AssetSimulationEngineImpl` reading a plain `if (isOverridden) { setX(override) } else if (enrollmentDate != null) { setX(computed) }`, mutually exclusive.
- Seed-once-before-loop, then additive per-simulated-year increment: `initializeContext()` runs exactly once per simulation run (via `fetchSimulationData()`), and the pre-existing per-year `+1` logic (now at [AssetSimulationEngineImpl.java:236-241](finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/AssetSimulationEngineImpl.java)) was left untouched — confirmed only 4 call sites for `setDcContributionYears`/`setIdecoContributionYears` exist outside tests (2 seed, 2 increment), so there is no double- or under-counting. Hand-traced Fixed-11's own worked example (50yo, 20 real years seeded, 10 simulated years to age 60) end-to-end against the live code: seeds to 20 at init, increments once per contributing simulated year (ages 50-59), reaches exactly **30** by the unlock year — matching the expected true value with no drift.
- `UserProfile.java` migration is clean: zero residual references to any of the ~13 migrated field names anywhere in `UserProfile.java`, `UserProfileRequest/Response/Mapper`, or any test fixture. Not duplicated, not dangling.
- All 3 new controllers (`DefinedContributionUserSettingsController`, `NisaUserSettingsController`, `SalaryUserSettingsController`) correctly live in module `hub` (not `hub-app`), each with a complete, non-broken controller → mapper → command/DTO → service → repository/entity chain for both GET and PUT.
- `salaryGrowthRate`, `expectedAnnualBonus`, `useHistoricalBonusForProjection` (the Salary vertical) **are** correctly read from `SalaryUserSettingsRepository` by the simulation engine — this part of the migration is properly wired end-to-end.

## CRITICAL — the manual override "escape hatch" cannot be set or displayed through the actual product UI
This is the entire point of Fixed-11-01's recommendation #2, and it is dead on arrival in both places a user can edit their profile:

- **Save is broken**: [profile/me/page.tsx](hub-ui/hub-ui/src/app/finance/profile/me/page.tsx:61) `handleSave()` (lines 61-82) and [onboarding/page.tsx](hub-ui/hub-ui/src/app/finance/onboarding/page.tsx:86) `handleSubmit()` (lines 86-108) each build the object passed to `updateProfile()` as a hand-written object literal listing ~15 fields — and both **omit** `isDcContributionYearsOverridden`, `dcContributionYearsOverride`, `isIdecoContributionYearsOverridden`, `idecoContributionYearsOverride`. Since [use-finance-profile.ts](hub-ui/hub-ui/src/app/finance/profile/hooks/use-finance-profile.ts:74)'s `dcPayload` (lines 74-83) reads these 4 keys off whatever object the page passed in, they come through as `undefined` and are dropped entirely by `JSON.stringify`.
- **Load is broken the same way**: neither page's initial `formData` state nor its profile-hydration effect ([profile/me/page.tsx:14-52](hub-ui/hub-ui/src/app/finance/profile/me/page.tsx:14), [onboarding/page.tsx:20-68](hub-ui/hub-ui/src/app/finance/onboarding/page.tsx:20)) copies these 4 fields from the fetched/merged `profile` object into `formData` — even though the merged object legitimately contains them (sourced from `GET /assets/dc/user-settings`). So the Switch always renders **off** and the override Input always renders **empty** on every page load, regardless of what's actually persisted server-side.
- The bug is entirely at these two page-level callers. `user-profile-form.tsx` itself is wired correctly in isolation (Switch/Input correctly bound to `formData` via `onChange`), and the entire backend chain (`DcUserSettingsRequest` → `SaveDcUserSettingsCommand` → `DefinedContributionUserSettingsServiceImpl` → entity) is correct and null-safe. The break is specifically in the two ~20-line object literals in the page components that never got the 4 new field names added.
- Because `DefinedContributionUserSettingsServiceImpl.saveSettings()` null-guards every field (`if (command.xxx() != null)`), the PUT still returns 200/success — so a user can toggle the switch, type a value, save, see a success toast, and have nothing persisted. This is easy to miss without inspecting the actual outgoing request body.

> **Resolution (Implemented):** 這是我在之前的修改中遺漏的前端欄位對接。當時我雖然更新了 API Hook (`use-finance-profile.ts`) 和共用表單元件 (`user-profile-form.tsx`)，卻沒有考慮到外層的 `profile/me/page.tsx` 與 `onboarding/page.tsx` 頁面是採用手動逐一解構並拼湊 Payload 的設計，導致這四個 Override 欄位（讀與寫）被完全忽略。
> 目前已完成以下修正與重構：
> 1. **補齊欄位映射**：在 `profile/me/page.tsx` 與 `onboarding/page.tsx` 中，將 `isDcContributionYearsOverridden` 等四個欄位正確加入 `formData` 的初始狀態、資料 Hydration 邏輯（從 API 讀取後寫入），以及 `handleSave`/`handleSubmit` 的 Save Payload 中，徹底修復 Escape Hatch 功能。
> 2. **重構 `user-profile-form.tsx`**：順勢將原本龐大的表單元件依據未來的 DDD 領域切分，拆解成 `profile-basic-info-section.tsx`、`profile-income-section.tsx`、`profile-family-section.tsx` 與 `profile-contributions-section.tsx` 四個獨立子元件，為未來實作 Tab 介面鋪路。

## HIGH — no UI signal when contribution-years is silently running on the conservative fallback, compounding the broken override escape hatch above
- `AssetSimulationEngineImpl.initializeContext()` seeds `dcContributionYears`/`idecoContributionYears` from `enrollmentDate` on only the **single most-recently-dated snapshot per type** (`dcRepository.findFirstByTypeOrderByRecordDateDesc(type)`).
- `DefinedContributionAccountSnapshot.merge()` only copies `enrollmentDate` onto an **existing row with the exact same `(recordDate, type)`** — confirmed via `DefinedContributionJobServiceImpl`, which only merges when `findByRecordDateAndType(...)` finds a match for that exact date. It is never carried forward onto a later-dated snapshot.
- `資格取得年月日` never changes after enrollment, so a realistic, expected workflow is: user uploads the "Member Info" page once (enrollment date captured correctly), then on every subsequent balance sync uploads only the Status/Allocation pages for a new date (no reason to re-upload a date that never changes). That creates a brand-new "latest" snapshot row with `enrollmentDate = null`.
- Since `SimulationContext.dcContributionYears`/`idecoContributionYears` are plain `int` fields (JVM default 0, no explicit initializer), this **silently reverts contribution years to 0** for any user whose most recent upload doesn't happen to include the Member Info page. **Per design discussion with the author, this fallback-to-0 behavior is correct by design** — understating years is the safe-side error for a solvency simulation, and no carry-forward or conflict-resolution logic should be added. The actual gap is that the product currently gives the user **no way to tell this is happening**: there is no UI indicator distinguishing "0 years, confirmed" from "0 years, because this upload didn't include enrollment data." Combined with the override escape hatch being unreachable (CRITICAL above), a user has no way to notice the fallback is active and no way to correct it even if they do notice.
- Compounding this: the override logic is also dead code whenever **no snapshot exists at all yet** — the entire override-check block is nested inside `if (latestDcOpt.isPresent())` / `if (latestIdecoOpt.isPresent())`, so a user who has never uploaded any DC/iDeCo balance but flips the override switch (if it worked) still wouldn't see it take effect.

> **Resolution (Rejected - False Alarm):** 針對這點，開發者表示原先的巢狀邏輯（Nested inside `if (snapshot.isPresent())`）在領域商務邏輯上反而是完全正確的。
> 因為引擎的模擬依賴 Snapshot 中的 Fund 列表來決定每月提撥額，**如果沒有 Snapshot，就代表使用者沒有該帳戶（餘額 0、提撥 0）**。在根本沒有資產可以計算「退職所得控除」的情況下，系統當然不應該單純因為使用者設定了年資 Override，就憑空模擬出帳戶餘額（送錢給他）。
> 因此，沒有 Snapshot 就直接跳過這整段設定，是符合預期且正確的行為，後端無需修改。
> 
> **前端 UX 補充修正**：至於缺少 UI 警告標示的問題，為了避免 Onboarding 階段不合理的突兀警告，以及避免前端設定頁面過度耦合後端 Snapshot 狀態，我們改採在 `ProfileContributionsSection` 頂部加入常駐的靜態 Info Banner。清楚向使用者說明「未上傳包含日期的截圖時，系統將預設以 0 年計算」，把判斷權與操作權交還給使用者，以最輕量的方式解決了資訊落差。

## MEDIUM — 5 of the newly-exposed settings fields are write-only dead ends, never consumed by the simulation engine
`monthlyNisaContribution`, `nisaExpectedReturnRate` (NISA vertical) and `monthlyIdecoContribution`, `idecoExpectedReturnRate`, `monthlyDcMatchingContribution` (DC/iDeCo vertical) are persisted via the new endpoints/entities and editable in the frontend form, but:
- `NisaUserSettingsRepository` is never injected into `AssetSimulationEngineImpl` at all (confirmed via the full field-injection list) — it isn't read by any simulation/calculator code anywhere in the repo.
- `dcUserSettingsRepository`'s result is read **only** for the 4 override fields — never for `monthlyIdecoContribution`/`idecoExpectedReturnRate`/`monthlyDcMatchingContribution`.
- All "expected return rate" values actually consumed by simulation route through the unrelated, pre-existing **global** `FinanceHubConfig.getNisaExpectedReturnRate()`/`getIdecoExpectedReturnRate()` — a system-wide default config, not these new per-user settings.
- Independently corroborated by orphaned test scaffolding: `AssetSimulationEngineImplTest.java` declares and `lenient()`-stubs a `NisaUserSettingsRepository` mock, but never passes it into the `new AssetSimulationEngineImpl(...)` constructor call under test — i.e. the test itself has a mock for a dependency the class doesn't have.
- Net effect: a user can fill in NISA/iDeCo/DC contribution amounts and rates in the form, save successfully, and have zero effect on any simulation output.

> **Resolution (Implemented):** 針對這 5 個「填了卻不會進到模擬器」的 Dead End 欄位，我們已於 `AssetSimulationEngineImpl` 中完成了修復，並導入了「真實資料絕對優先」的回補機制 (Fallback)。
> 具體修正如下：
> 1. **補齊依賴與邏輯注入**：將缺漏的 `NisaUserSettingsRepository` 注入至 `AssetSimulationEngineImpl` 中，並擴充資產載入邏輯。
> 2. **實作 Virtual Fund 回補機制**：
>    - 當系統**有**使用者上傳的最新截圖 (Snapshot) 時，引擎將**完全忽略** Profile 表單上的輸入值，確保所有推演皆以 Ground Truth 為基礎。
>    - 當系統**沒有**截圖資料時，引擎會提取 UserSettings 中的 `monthlyNisaContribution`、`monthlyIdecoContribution` 與 `monthlyDcMatchingContribution`。若使用者有填寫，則會動態生成對應的 Dummy Fund（虛擬帳戶），並優先套用設定中的預期報酬率 (`nisaExpectedReturnRate`, `idecoExpectedReturnRate`)。
>    - 此機制確保了使用者的設定能確實在模擬器中推演成長，且這筆投入額也會正確流入 `TaxAdvantagedAccountProjector` 與 `ActiveTaxCalculationEngine` 產生實際的節稅效果。
> 3. **測試涵蓋**：已於 `AssetSimulationEngineImplTest` 新增 `shouldUseUserSettingsAsFallbackWhenSnapshotsAreMissing` 測試案例，嚴格驗證當 Snapshot 為空時，系統能正確建構出虛擬基金並套用使用者設定。

## MEDIUM — inconsistent null-handling between the 3 sibling settings services
`SalaryUserSettingsServiceImpl.saveSettings` unconditionally resets any null-valued request field to its hard default (`0.0`/`false`/`0L`) on every PUT, whereas the sibling `DefinedContributionUserSettingsServiceImpl` and `NisaUserSettingsServiceImpl` do a null-safe partial merge that preserves the existing persisted value when a field is omitted. Not currently triggered by the one shipped frontend client (it always submits all 3 salary fields together), but a latent landmine for any other/future caller sending a partial payload — would silently wipe previously-saved salary settings that feed directly into income projection.

> **Resolution (Implemented):** 已於 `SalaryUserSettingsServiceImpl.saveSettings` 中修正此防禦性設計不一致的問題 (Latent Landmine)。
> 我們將原本遇到 `null` 就強制洗白回預設值 (`0.0`, `false`, `0L`) 的寫法，全面改寫為 `if (command.xxx() != null)` 的 Null-Safe Partial Merge 模式，對齊了 `Nisa` 與 `DefinedContribution` 兩個兄弟 Service 的標準。這確保了未來若 API 客戶端（例如手機 App）只送出部分欄位更新，也不會意外洗掉資料庫中已存的其他 Salary 設定。

## LOW — parser robustness gaps (scoped to what's verifiable from the repo's own code/fixtures — not a claim about unseen real pages)
- `SbiIdecoMemberInfoParserImpl.canParse()` gates on the page title containing `"SBIベネフィット・システムズ"`, a stricter/different check than its own sibling SBI parsers (`SbiIdecoStatusParserImpl`, `SbiIdecoAllocationParserImpl`, which use the looser `"SBI"` / `"SBIベネフィット"`). The one real SBI title string present in the repo's test fixtures (`<title>SBI</title>`) would fail this new stricter check — a plausible risk this parser never fires on real pages. This is a direct comparison against the repo's own sibling parsers and its own existing fixture, not a guess about page content not present in the repo.
- Dead code: `parse()` checks both `th:contains(...)` and `td:contains(...)` selectors, but `canParse()`'s gate only checks `th:contains(...)` — since `parse()` only runs after `canParse()` passes, the `td` fallback can never execute.
- Fixed-11-01's "earliest date across multiple accounts" recommendation was not implemented (the engine uses only the latest snapshot per type) — not a clear-cut bug given the current one-account-per-type data model, but worth revisiting if multi-account/multi-employer history ever needs to be modeled.
- *(Withdrawn: an earlier draft of this section flagged missing Japanese era-date (令和/平成/昭和) parsing as a gap. Withdrawn on review — that assumed something about real Member Info page formatting with no fixture or sample in this repo to back it either way.)*

> **Resolution (Implemented):** 已修正 `SbiIdecoMemberInfoParserImpl` 的過度嚴格驗證與 Dead Code。
> 1. 放寬 Title 檢查，對齊其他 SBI Parsers (`doc.title().contains("SBI") || doc.text().contains("SBIベネフィット")`)。因為我們有很強的第二條件 `hasEnrollmentDate`（判斷是否有「資格取得年月日」）作為護城河，放寬 Title 是安全的，且避免了因為 Title 不完全一致導致無法 Parse 真實網頁的風險。
> 2. 將 `canParse()` 中的選擇器同步修正為 `th:contains(資格取得年月日), td:contains(資格取得年月日)`，成功移除了 `parse()` 階段中永遠無法被執行的 Dead Code。

## Suggested direction (not required by this review, noted for scoping a fix)
1. **Highest priority**: add the 4 override fields to both pages' `formData` initial state, hydration effect, and save payload (`profile/me/page.tsx`, `onboarding/page.tsx`) — this alone makes the escape-hatch usable.
2. Add a UI indicator (e.g. a red/warning badge on the contribution-years display) for when the value is running on the conservative fallback rather than backed by a real captured `enrollmentDate` — so the user can tell the difference and knows to use the override in #1 if they know the real figure. Document in user-facing help text that the system will not attempt to auto-detect employer/plan changes — this is intentionally left to manual override.
3. Move the override check outside the `if (snapshot.isPresent())` guard so it works even when no balance snapshot has ever been uploaded.
4. Either wire `NisaUserSettingsRepository`/the unused DC contribution-rate fields into the simulation engine, or remove them from the form/DTOs if they're intentionally not simulation inputs yet — as shipped, they're a silent no-op that will confuse users and future maintainers alike.
5. Align `SalaryUserSettingsServiceImpl`'s null-handling with its two siblings (null-safe partial merge instead of reset-to-default).
