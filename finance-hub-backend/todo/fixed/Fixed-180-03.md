# [FIXED] 180-03：Amazon/Rakuten/Sofmap訂單項目領域——重新匯入同一張訂單時，訂單底下的商品項目被整批`items.clear()`砍掉重建，使用者透過NotebookLM設定好的`category`跟著一起消失；修法是改成逐項目比對（用`name`+`unitPrice`找既有項目），不整批清空重建

Rakuten、Sofmap的domain結構相同（`RakutenOrder`/`SofmapOrder`都繼承`BaseOrder`，商品項目都繼承`BaseOrderItem`），對應的`RakutenServiceImpl`/`SofmapServiceImpl`走同樣的模式。

## 現狀
訂單本身（`AmazonOrder`/`RakutenOrder`/`SofmapOrder`）已經有平台核發的真實穩定商務ID——`orderId`，這一層的比對沒有問題，重新匯入同一張訂單時能正確找到既有訂單。

問題在訂單底下的「商品項目」清單（`BaseOrderItem`，被`AmazonItem`等繼承）：現有程式碼在重新匯入同一張訂單時，是把這張訂單底下的`items`整批`clear()`掉再重新加入解析出來的新項目——這會讓每個項目上的`category`（透過NotebookLM等外部工具批次分類寫入）一起被清空。

查證確認`AmazonExtensionController`跟後端job import（`AmazonJobServiceImpl`）最終都會呼叫同一個`AmazonServiceImpl.saveOrder`方法去合併既有訂單跟新解析結果，Rakuten、Sofmap的結構相同——這代表這個問題不只影響系統管理者跑job import，也會影響一般使用者透過Extension重新打開同一張訂單頁面送出的情況（跟銀行/信用卡領域「Extension走完全獨立路徑、不受job import的merge邏輯影響」不同）。

## 為何是問題
訂單底下的商品項目一旦被整批`clear()`重建，不管重新匯入的原因是什麼（補發對帳單、重新確認明細、或Extension重新爬取同一張訂單頁面補上出貨日），`category`都會被連帶清空。因為job import跟Extension共用同一條合併路徑，這個問題不是只有系統管理者會踩到——一般使用者透過Extension重新打開同一張訂單頁面（例如出貨後補上`shippingDate`）送出時，一樣會觸發這個整批清空的行為，一樣會丟失自己或NotebookLM已經設定好的`category`。

## 具體錯誤情境
使用者透過Extension在Amazon訂單確認頁面送出一張訂單的資料，裡面有三個商品項目，之後透過NotebookLM批次設定好這三個項目的`category`（例如日用品、書籍、3C配件）。幾天後商品出貨，使用者再次打開同一張訂單頁面（這次頁面上多了出貨日期），讓Extension重新送出——因為訂單編號相同，`AmazonServiceImpl.saveOrder`找到既有訂單並呼叫合併邏輯，現有程式碼的`items.clear()`會把這三個商品項目整批砍掉再重建，三個項目的`category`全部消失，使用者必須重新設定一次分類。

## 建議修正方向
這裡列出修法的具體設計，不是多個方向選一——這是這個領域唯一需要新寫的部分：

**訂單項目改成逐項目比對，不整批清空重建：**
1. 用`name`+`unitPrice`這組複合鍵，在這張訂單既有的項目清單裡找有沒有符合的既有項目。這套比對鍵的可靠度遠高於銀行/信用卡那組「日期+金額+店名」——`name`+`unitPrice`只是在同一張訂單底下（已經用`orderId`鎖定範圍）的少數幾個商品之間做區分，不是在全資料庫範圍內用日期去猜。
2. 找到：用這次解析結果覆蓋事實欄位（`quantity`、`seller`、`itemId`等），`category`維持既有值不變。
3. 找不到：當作這張訂單這次新出現的項目，新增一筆，`category`為空。
4. 既有項目清單裡，有沒有被這次解析結果比對到的項目——代表這次對帳單/頁面不再列出這個項目（可能是訂單被部分退貨、或單純解析結果跟上次不同），這種「孤兒項目」要不要保留或移除，留給實際落地時決定，不是這份issue要拍板的範圍。

因為job import跟Extension共用同一條`saveOrder`合併路徑，這套逐項目比對一旦套用，會同時讓系統管理者（job import）跟一般使用者（Extension）都受益——一般使用者透過Extension重新打開同一張訂單頁面送出時，一樣能保留`category`不被清空，不是只對系統管理者有利的設計。

## 這份文件沒有解決的部分
- **孤兒項目的處理方式**：見上方比對流程第4點，這份issue沒有拍板。
- **這套比對鍵要不要延伸到三平台以外（例如未來新增的購物平台）**：這份issue只確認Amazon/Rakuten/Sofmap三平台domain結構相同（都繼承`BaseOrder`/`BaseOrderItem`）可以套用同一套設計，其他平台待個案確認。
