## 修改1：`PreviousYearTaxRecord.java`——新增一個欄位裝「退休當年在職段YTD差額」

## 修改2：`YearlySimulationPipeline.calculateTaxesAndBuildResult`——分流邏輯改成兩段式

**不要修改`applyWorkingTaxes`、`applyRetireeTaxes`這兩個方法本身的內部計算邏輯**（它們內部怎麼算稅不用動）——要修改的是呼叫它們的進入條件、呼叫時傳入的月份數，以及呼叫完之後怎麼合併結果。

### 新增一個判斷：這一年退休月是幾月（如果今年是退休年）
在`calculateTaxesAndBuildResult`最前面（或是在`processSimulationYear`裡、傳進`calculateTaxesAndBuildResult`之前）新增：
```java
boolean isRetirementYear = (age == targetRetirementAge); // 現有判斷依據，不是新邏輯
Integer retirementMonth = null;
if (isRetirementYear) {
    retirementMonth = RetirementMonthResolver.resolveRetirementMonth(
            context.getProfile() != null ? context.getProfile().getBirthDate() : null,
            context.getConfig().getRetirementMonthMode());
    // retirementMonth 為 null 時（birthDate缺失），退回現行行為：整年視為退休，
    // 等同於 retirementMonth = 1（在職段0個月，跟現行 applyWorkingTaxes 整段跳過的結果一致）。
}
```
`targetRetirementAge`已經是`calculateTaxesAndBuildResult`的既有參數（[YearlySimulationPipeline.java:67-70](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/pipeline/YearlySimulationPipeline.java)的`processSimulationYear`簽名已經接收這個參數,只是目前`calculateTaxesAndBuildResult`簽名沒有轉傳——需要把`targetRetirementAge`也加進`calculateTaxesAndBuildResult`的參數列表）。

### 三種情境，分開處理：
1. **這一年不是退休年**（`age != targetRetirementAge`）：完全維持現狀，呼叫`applyWorkingTaxes`或`applyRetireeTaxes`其中一個（由現有的`context.isRetired()`互斥判斷決定），不受這份文件影響。
2. **這一年是退休年，且`retirementMonth == 1`（或`birthDate`缺失導致退回整年退休）**：等同於現行行為，只呼叫`applyRetireeTaxes`，`applyWorkingTaxes`不呼叫。不產生`pendingWorkingSegmentTaxAdjustment`。
3. **這一年是退休年，且`retirementMonth`在2-12之間**：**`applyWorkingTaxes`跟`applyRetireeTaxes`都要呼叫**，各自算出自己這一段的稅額，結果相加寫回`state`一次。

### 情境3的具體改法

**呼叫`applyWorkingTaxes`，但`monthsToAdd`要換算成「退休月之前的月數」**：
```java
int workingMonthsBeforeRetirement = retirementMonth - 1; // 退休月之前有幾個月在職
```
這個數字要傳進`applyWorkingTaxes`裡呼叫`calculateSalaryForYear`的地方——**不是修改`applyWorkingTaxes`方法本身，是修改呼叫它之前，`effectiveAnnualSalary`怎麼算出來的那一段**（[YearlySimulationPipeline.java:108-118](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/pipeline/YearlySimulationPipeline.java)）。這段現有邏輯要改成：如果是情境3，`salaryMonthsToAdd`（或非起算年時傳給`calculateSalaryForYear`的月數參數）要用`workingMonthsBeforeRetirement`，不是用現行的`monthsToAdd`（過渡年專用）或「不傳月數參數=整年12個月」（非過渡年時現行的`calculateSalaryForYear(context, careerEvents)`兩個參數版本，不傳月數=預設整年）。這代表非過渡年份的退休年，`calculateSalaryForYear`要改用帶月數參數的那個overload（第64-134行那個四參數版本），不能用第60-62行那個兩參數版本（兩參數版本內部呼叫`calculateSalaryForYear(context, careerEvents, null, null)`，`monthsToAdd=null`代表整年，不符合退休年需求）。

`applyWorkingTaxes`方法本身的進入條件`if (!context.isRetired() && effectiveAnnualSalary > 0)`——**這裡有一個需要注意的衝突：`context.isRetired()`在[processSimulationYear第73行](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/pipeline/YearlySimulationPipeline.java)已經被設成`age >= targetRetirementAge`，退休年當年這個值是true，會導致`applyWorkingTaxes`現有的進入條件擋住自己**。這代表情境3不能直接呼叫現有的`applyWorkingTaxes`方法——要幫這個方法新增一個變體（或修改進入條件，額外允許「這一年是退休年且有在職段」這種情況進入），讓它在`isRetired()`為true、但目前是在算退休月之前的在職段時，依然執行內部的稅額計算。具體做法：把第160行的進入條件`if (!context.isRetired() && effectiveAnnualSalary > 0)`改成`if ((!context.isRetired() || isHandlingPreRetirementSegment) && effectiveAnnualSalary > 0)`，`isHandlingPreRetirementSegment`是新增的方法參數，由情境3的呼叫處傳`true`，其他呼叫處（情境1、2）傳`false`。

**呼叫`applyRetireeTaxes`，`monthsToAdd`換算成「退休月之後的月數」**：
```java
int pensionMonthsAfterRetirement = 12 - retirementMonth + 1;
```
傳進`applyRetireeTaxes`現有的`monthsToAdd`參數——第232行`if (age == initialAge && monthsToAdd < 12)`這個條件要改成`if (pensionMonthsAfterRetirement < 12)`（不限於`age == initialAge`，見上面「現狀」第3點），讓既有的比例折算邏輯在任何退休年都生效，不只是起算年。

**兩段結果相加，寫回`state`一次**：
```java

long workingSegmentInhabitantTax = ...;
long workingSegmentSocialInsurance = ...;
```

**這代表`applyWorkingTaxes`跟`applyRetireeTaxes`這兩個方法簽名需要調整**，不能繼續用現在這種「直接改`state`」的寫法——情境3底下，兩個方法都需要先把算出來的數字回傳（或寫進一個暫存變數），等兩段都算完才一次性合併寫進`state`。建議的做法：讓這兩個方法回傳一個小物件（例如重用`TaxCalculationResult`，`ActiveTaxCalculationEngine.calculate`/`calculatePensionTax`本來就回傳這個型別），呼叫端自己決定要不要把兩段結果加總——情境1、2繼續用現行「方法直接set`state`」的寫法（不想大動既有行為），只有情境3額外寫一段「呼叫兩次、各自拿到`TaxCalculationResult`、相加後統一set」的新邏輯，不強迫改動現有兩個方法的內部實作。

## 修改3：`applyYearEndAdjustment`——退休當年不呼叫，改成計算YTD差額並包進`PreviousYearTaxRecord`

[YearlySimulationPipeline.java:150](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/pipeline/YearlySimulationPipeline.java)現有呼叫：
```java
applyYearEndAdjustment(context, state, age, initialAge, effectiveAnnualSalary);
```

**改成依情境分流**：
- **情境1、2**（不是退休年，或退休年但`retirementMonth==1`整年退休）：維持現狀呼叫`applyYearEndAdjustment`，不改變既有行為（起算年的過渡年YTD調整邏輯，跟這份文件無關，不要動）。
- **情境3**（退休年，`retirementMonth`在2-12之間，**且這一年同時是模擬起算年**，即`age == initialAge`）：**不呼叫`applyYearEndAdjustment`**。改成一段新邏輯，算出在職段的YTD差額，包進`PreviousYearTaxRecord`的新欄位`pendingWorkingSegmentTaxAdjustment`：

```java
// 只在 age == initialAge 時才有意義——因為 ytdXxx 這些欄位只有起算年有真實數據。
// 退休發生在未來某一年（不是起算年）的話，沒有YTD可比較，在職段算出來的就是最終結果，
// 不需要這段差額調整。
if (age == initialAge) {
    long ytdSocialInsurance = context.getYtdHealthInsurance() + context.getYtdPension()
            + context.getYtdEmploymentInsurance();
    long trueWorkingSegmentIncomeTax = workingSegmentIncomeTax; // 上面情境3算出來的在職段稅額
    long trueWorkingSegmentInhabitantTax = workingSegmentInhabitantTax;
    long trueWorkingSegmentSocialInsurance = workingSegmentSocialInsurance;

    long incomeTaxDiff = trueWorkingSegmentIncomeTax - context.getYtdIncomeTax();
    long inhabitantTaxDiff = trueWorkingSegmentInhabitantTax - context.getYtdResidentTax();
    long socialInsuranceDiff = trueWorkingSegmentSocialInsurance - ytdSocialInsurance;
    long totalAdjustment = incomeTaxDiff + inhabitantTaxDiff + socialInsuranceDiff;
    // totalAdjustment > 0 代表YTD扣繳不足、隔年要追繳；< 0 代表YTD扣繳過多、隔年退稅。
    // 正負號在這裡先不要反轉，留給下面「隔年發放」那段程式碼統一處理方向。
```

  * 日本企業人事與就業規則壓倒性標準皆為「満65歳に達した日の属する月の末日をもって退職」（以年滿 65 歲當月之最後一天為退職日）。

  [`RetirementMonthResolver.resolveRetirementMonth(...)`](file:///Users/edward/Desktop/Projects/youtube-data-hub-wrapper/finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/model/RetirementMonthResolver.java) 回傳之月份 `M` 代表「最後在職月份」：

    * **DECEMBER 模式**（回傳 12）：全年在職 12 個月，年金月數 0 個月。視同全年在職，不進入退休年金段計算。若 `birthDate` 缺失，依現行規範亦回傳 12。

### 3. 跨年度在職段差額 `pendingWorkingSegmentTaxAdjustment` 規格與正負號統一定義

#### (1) 為何必須新增此欄位（必要性說明）
1. **真實世界制度背景（源泉徵收 vs 年末調整 vs 確定申告）**：
   - 受薪階級每月的薪水單皆由公司代扣「源泉徵收所得稅（Withholding Tax）」。此代扣稅率是依照「全年 12 個月皆有此月薪」的源泉徵收稅額表計算。
   - 若員工在**年中退休**（例如 6 月底離職），其全年在職薪資僅有 6 個月，年收入大幅縮水，原本每月按「年薪 12 個月」扣繳的稅額明顯**過度扣繳（超額預扣）**。
   - 在正常年底在職員工身上，公司會在 12 月進行「年末調整（Year-End Adjustment）」將超額扣繳之稅款直接退還於當月薪資。**但年中退休者在 12 月時已無雇主，雇主無法也不會替其辦理年末調整！**
   - 該退休者必須在**次年 2 ~ 3 月自行前往稅務署提出「確定申告（確定申告，Kakutei Shinkoku）」**，才能向國稅局取回在職段超額預扣的稅款。
2. **模擬器年步進金流機制**：
   - 財務模擬器是以「年（Year）」為步進單位。起算年中，使用者的銀行流動現金已預先扣除了已預扣金額（YTD Income Tax, YTD Resident Tax, YTD Social Insurance）。
   - 模擬器在年中退休年度算出在職段的真實理論應納稅額（True Tax）會遠低於 YTD。這筆「超額預扣應退回之差額」，在真實世界是隔年春季才會匯入銀行帳戶。
   - 若不透過跨年度稅務記錄（[`PreviousYearTaxRecord`](file:///Users/edward/Desktop/Projects/youtube-data-hub-wrapper/finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/model/tax/PreviousYearTaxRecord.java)）將該差額傳遞至隔年，並於隔年年初注入現金池，這筆退稅將憑空消失，導致模擬現金流失真。
3. **為何不能複用現有 `pendingKakuteiShinkokuRefund`**：
   - `pendingKakuteiShinkokuRefund` 在系統中具有非常嚴格且專屬的語意：它是「住宅貸款特別扣除（住宅ローン控除）第一年的確定申告退稅款」。
   - 房貸退稅具有法定的額度上限（房貸年末餘額 × 0.7%），且所得稅扣除不完的剩餘部分會轉移至次年度住民稅扣抵（`unusedMortgageDeductionForInhabitantTax`）。
   - 若將在職段薪資稅差額混入 `pendingKakuteiShinkokuRefund`，會污染房貸退稅計算，並導致房貸上限與住民稅轉移額度的判定完全失真。因此，獨立出 `pendingWorkingSegmentTaxAdjustment` 專款專用，是架構上最乾淨且最安全的設計。

#### (2) 正負號統一定義與公式修正（修正原文數學公式矛盾）
* **原文提議之矛盾**：
  * 原文提議 L220 使用公式：`totalAdjustment = (TrueTax - YTD)`（應納 - 已扣）。
    若已預扣 100 萬，理論應納只需 60 萬（應退稅 40 萬），公式計算結果為：`60 - 100 = -40`（**負數**）。
  * 然而，原文在隔年發放時（L256）卻寫道：`currentLiquidCash = cash + adjustment`，並備註「正數代表退稅加進現金」。
  * 這造成嚴重的數學符號矛盾：若退稅為負數，加進現金反而會導致退稅被誤扣現金！
* **統一修正後之正式公式**：
  為了與現金流完全對齊（**正數 = 退稅進帳 / Cash Inflow，負數 = 補繳出帳 / Cash Outflow**），公式嚴格定義為 **`YTD - TrueTax`（已預扣 - 理論應納）**：
  ```java
  long totalAdjustment = (context.getYtdIncomeTax() - trueWorkingSegmentIncomeTax)
          + (context.getYtdResidentTax() - trueWorkingSegmentInhabitantTax)
          + (ytdSocialInsurance - trueWorkingSegmentSocialInsurance);
  ```
  * **退稅（已預扣 > 理論應納）**：`totalAdjustment > 0`（正數）。隔年年初執行 `cash + totalAdjustment`，流動現金實質增加（退稅款入袋）。
  * **補繳（已預扣 < 理論應納）**：`totalAdjustment < 0`（負數）。隔年年初執行 `cash + totalAdjustment`，流動現金實質扣除（補繳稅款出帳）。
