## 針對什麼問題
系統模擬退休資產時，退休狀態目前是用`context.setRetired(age >= targetRetirementAge)`這個**整年二元**旗標判斷——不管使用者實際上是幾月退休，退休那一年整年都被當成「全年退休」處理。這導致：
1. 退休當年在職月份（例如1-5月）的薪資所得稅、住民稅、社會保險完全不會被計算（`applyWorkingTaxes`整段被`!context.isRetired()`擋住）。
2. 這段在職期間如果符合房貸抵稅資格，這筆抵稅額完全沒有機會被算出來、也沒有機會透過確定申告機制在次年復活。
3. 如果退休剛好發生在模擬起算年（過渡年），`applyYearEndAdjustment`這個「過渡年YTD稅額調整」機制，會錯誤地拿退休後的小額年金稅去跟退休前的真實YTD薪資稅相減，算出一個不合理的巨大負值（這部分已經獨立記錄成[issue-190](issue-190.md)，見下方「跟issue-190的關係」）。

## 查證確認的關鍵事實：不需要重寫整個模擬引擎
這是整份191討論裡最重要的收斂結論，所有下面的具體方向都建立在這個事實上：

- **`AssetSimulationEngineImpl`主迴圈不需要改**：主迴圈是`for (int age = currentAge; age <= targetAge; age++)`，一年跑一次。`retirementMonth`這個需求影響的不是這個迴圈的疊代次數，是「退休發生的那一年內部，要不要把這一年拆成在職段+退休段分別算」——其他39年完全不受影響，也不需要知道「月」這個概念存在。
- **稅務核心計算引擎不需要改**：`ActiveTaxCalculationEngine.calculate(...)`（算在職稅負）跟`calculatePensionTax(...)`（算年金稅負）兩個方法本身都是純函數——給多少所得，就依照年度級距規則重新算出對應的扣除額跟稅負，不是先假設一定是12個月的所得。這代表要讓退休年的在職段正確納稅，不需要修改這兩個方法本身，只需要改「誰呼叫它、傳了什麼所得進去」。
- **Grid Search/GA的計算量不會暴增**：Grid Search的`evaluate()`呼叫次數早就被`MAX_GRID_ENGINE_COMBINATIONS = 5000`這個硬上限鎖住（NISA/退休年齡/年金請領/iDeCo開始四個維度隨便乘一乘就遠超5000），不是真的窮舉搜尋空間。這次改動只讓「退休那一年」的內部計算稍微變貴一點，不影響outer loop的次數。

## 具體方向一：退休月份怎麼決定——用生日月或12月，不用新建事件機制
查證確認`UserProfile.birthDate`這個欄位（完整年月日）本來就存在、本來就隨著`SimulationContext.profile`這個欄位一路傳到計算所得稅/薪資的方法裡（`IncomeExpenseCalculator`、`ActiveTaxCalculationEngine`都已經在讀`context.getProfile()`）——只是`SimulationContextFactory`把`birthDate`轉成`currentAge`時，用`Period.between(...).getYears()`只取了年數，月份資訊在這一步被丟棄了。

**不需要讓使用者額外輸入一筆事件記錄去指定退休月份**，用一個系統設定層級的開關就能決定：
- 選項A：退休月份固定是`targetRetirementAge`歲那一年的**12月**。
- 選項B：退休月份固定是`targetRetirementAge`歲**生日當月**。

這個開關是全域、固定的規則，不需要為每個使用者的退休事件逐一判斷或輸入，也不用去查證各國/各公司定年退職慣例的細節差異（這類細節容易沒完沒了，刻意不處理）。實作上不需要新增`SimulationContext`欄位——`context.getProfile().getBirthDate().getMonthValue()`在需要的地方直接讀就有。

## 具體方向二：退休那一年的稅務計算——在職段用真實所得重新算，不是打折
退休當年（如果退休月不是1月）的計算流程：
1. **在職段**（退休月之前）：用這段期間的真實所得（薪資、獎金）呼叫一次`ActiveTaxCalculationEngine.calculate(...)`，正確算出這段期間的所得稅、住民稅、社保、以及（如果有房貸）`kakuteiDeduction`。**不是把全年稅負乘上比例去打折**——因為所得稅的扣除額/稅率是非線性的（級距式），打折會失真；是直接把這段期間的真實所得當作輸入，讓這個方法自己重新查表算出正確答案。社會保險（健康保険/厚生年金）因為費率結構是線性的（月薪×固定費率），用真實所得去算天然就是正確的部分年結果，不需要特殊處理。
2. **退休段**（退休月之後）：用剩餘月份的年金所得呼叫`calculatePensionTax(...)`——這部分`applyRetireeTaxes`裡已經有比例折算邏輯（`age == initialAge && monthsToAdd < 12`那一段），不需要修改。
3. 兩段的`netIncome`、各項稅額加總成這一年最終要回傳的結果。

**真正要修改的範圍，侵限在`YearlySimulationPipeline.calculateTaxesAndBuildResult`這個方法內部的分流邏輯**——判斷「這一年有沒有發生退休事件、退休月是幾月」（用方向一的開關去推算），如果有，就把`applyWorkingTaxes`跟`applyRetireeTaxes`都各自呼叫一次（各自帶上正確的部分年所得跟月份數，取代現在互斥的`if/else`寫法）；沒有發生退休事件的年份，維持現狀完全不變。

### 差額最終在隔年透過確定申告結清，不是在退休當年立刻結清
在職段算出來的理論正確稅負，跟這段期間已經被公司實際扣繳的金額之間，如果有落差（該退稅或該追繳），不會在退休當年被結清——而是跟房貸的`kakuteiDeduction`一樣，包進`PreviousYearTaxRecord`這個既有的跨年記錄（現在這個記錄只裝房貸抵稅額，所得稅/住民稅的差額需要新增進這個記錄的欄位），隔年才透過確定申告的現金流發放邏輯一次性處理。追繳跟退稅都適用同一條規則，不分正負——這個機制依據的是「退休當年年底還有沒有雇主」，不是差額的正負號：退休的人今年底沒有雇主可以幫忙結清，不管是該退稅還是該追繳，都沒有「當年由公司結清」這個選項可用。

這筆遞延的差額，隔年發放時走的是跟現有房貸退稅同一條路——直接加進`currentLiquidCash`這個現金欄位，不會寫回`estimatedIncomeTax`等稅額欄位。查證確認使用者在「算出差額的那一年」目前不會看到任何預告訊息，只會在隔年發現現金池數字變多或變少，沒有任何文字說明來源——這個透明度缺口本來就存在於現有的房貸確定申告退稅機制，不是這份方向新造成的。要不要新增預告機制，是跟這個決定無關的獨立功能，不在這份文件的範圍內。

Grid Search/GA判斷「破產」的方式是逐年檢查現金有沒有瞬間變成負數，不是只看模擬結束時的總資產，現金一旦變負會立刻觸發強制變賣股票/NISA去補足赤字。這代表差額遞延到隔年，會改變「哪一年的現金健康程度被系統看到」——退稅遞延可能讓退休當年看起來比真實情況更緊繃，追繳遞延則讓退休當年看起來比真實情況更寬裕、隔年才變緊。這點在實作驗證時需要留意，但不影響這裡已經確定要採用的結清方式。

## 具體方向三：房貸確定申告自動復活——要覆蓋退休後的每一年，不是只覆蓋退休當年
真實世界裡，退休的人完全沒有年末調整這個環節——不管是退休當年還是退休後第幾年，房貸控除額能不能扣抵、扣不完的部分要不要結轉到隔年確定申告，每一年都要處理，不是只在退休當年處理一次就結束。查證確認的現有機制跟缺口如下：

**「發放」這一半已經支援年與年之間無限串接，不需要修改**：查證[YearlySimulationPipeline.java:80-97](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/pipeline/YearlySimulationPipeline.java)，每年開頭讀取`PreviousYearTaxRecord`、把`pendingKakuteiShinkokuRefund`當現金發放這段邏輯，完全不檢查退休狀態——不管退休第幾年，只要上一年留下了記錄，這一年就會正常把錢發出來，這一段本來就能無限串接。

**缺的是「產生」這一半，而且退休之後整段空白**：`PreviousYearTaxRecord`唯一的產生點在`ActiveTaxCalculationEngine.calculate(...)`內部（[ActiveTaxCalculationEngine.java:228-262](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/tax/ActiveTaxCalculationEngine.java)），這個方法只會從`applyWorkingTaxes`被呼叫。退休之後整年只會呼叫`calculatePensionTax(...)`（[ActiveTaxCalculationEngine.java:338-389](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/tax/ActiveTaxCalculationEngine.java)），這個方法完全不接收房貸參數，也沒有任何地方打包`PreviousYearTaxRecord`。這代表方向二只解決了「退休當年→隔年」這一次串接，從退休第2年開始，「產生」這個環節完全空白，房貸計算器每年仍會正常算出控除額（查證確認`MortgageCalculator`不檢查退休狀態），但這筆錢沒有管道被扣抵或結轉，直接消失。

這個缺口不只影響`kakuteiDeduction`（本年度沒扣完、隔年當現金發放）這一條線：`unusedMortgageDeductionForInhabitantTax`（本年度沒用完、結轉抵未來年度住民稅，[ActiveTaxCalculationEngine.java:241-244](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/tax/ActiveTaxCalculationEngine.java)）的唯一消費點也同樣只在`calculate(...)`內部——退休前如果留下一筆還沒用完的住民稅結轉額，退休後同樣會卡住、永遠不會被消費。

**修法方向：讓`MortgageCalculator`在分類控除額的源頭就知道退休狀態，退休時全部歸進`kakuteiDeduction`，不是在下游額外補一層判斷**。查證[MortgageCalculator.java:355-363](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/calculator/MortgageCalculator.java)確認，這兩個欄位的分類依據目前只有「今年是不是入住第一年」（`isOccupancyYear`）——入住第一年控除放`kakuteiDeduction`，入住第二年起放`yearEndDeduction`（代表系統預期這筆會被公司年末調整吃掉）。這個分類完全不知道使用者今年是不是退休：一個已經退休超過一年、入住房屋也超過一年的人，控除會被歸類成`yearEndDeduction`，但退休的人沒有公司可以辦年末調整去吃掉這筆——如果退休段只處理`kakuteiDeduction`而放著`yearEndDeduction`不管，這筆錢一樣會不見。

與其在下游（`applyRetireeTaxes`）額外寫一段「兩個欄位加總再封頂」的邏輯去補救，更簡單的做法是直接修正分類判斷本身：退休時不管入不入住第一年，控除額一律歸進`kakuteiDeduction`，`yearEndDeduction`固定是0——這需要讓`MortgageCalculator`新增一個輸入（例如讀取`context.isRetired()`，這個方法本來就接收`context`），判斷邏輯從「只看`isOccupancyYear`」改成「退休了就全部進`kakuteiDeduction`，否則維持原來『入住第一年進`kakuteiDeduction`、之後進`yearEndDeduction`』的判斷」。

這樣改完全不需要修改`ActiveTaxCalculationEngine.calculate(...)`裡既有的扣抵邏輯：查證[ActiveTaxCalculationEngine.java:228-231](file://finance-hub/finance-hub-backend/hub-app/src/main/java/ch/lin/finance/hub/backend/api/app/service/simulation/core/tax/ActiveTaxCalculationEngine.java)確認，這段本來就是接力處理——先用`yearEndDeduction`扣`baseIncomeTax`，再用剩下的`baseIncomeTax`幫`kakuteiDeduction`封頂（`actualKakuteiRefund = Math.min(baseIncomeTax, kakuteiDeduction)`）。既然`yearEndDeduction`在退休段永遠是0，第一步什麼都不會發生，直接跳到用完整的`baseIncomeTax`幫`kakuteiDeduction`封頂——這正好就是我們已經確認的方向（用當年稅負封頂、超過的部分轉住民稅結轉），不需要額外寫判斷去合併兩個欄位。`calculatePensionTax`同樣不需要接收房貸參數去改變年金稅負本身，`applyRetireeTaxes`需要額外呼叫一次`MortgageCalculator`已經算出來的`kakuteiDeduction`，用這一年的年金`baseIncomeTax`封頂後，才打包進`PreviousYearTaxRecord`。

**還留著一個介面層級的缺口，尚未定案**：拆解到程式碼規格的程度時（見[question-191-04](question-191-04.md)）發現，`calculatePensionTax`目前的回傳物件`TaxCalculationResult`只有`incomeTax`/`inhabitantTax`/`socialInsurance`/`netIncome`四個欄位，沒有回傳封頂前的`baseIncomeTax`——而上一段說的「用這一年的年金`baseIncomeTax`封頂」，呼叫端目前拿不到這個數字。191-04列出了兩個選項（幫`TaxCalculationResult`新增欄位；或讓`calculatePensionTax`直接接收房貸參數、在內部做完封頂），兩個選項的取捨還沒有查證清楚，留給之後決定，見191-04的「修改2」。

## 跟issue-190的關係：190描述的情境在這份方向落地後不會再發生，不需要照190原本的方案去修
issue-190描述的場景是：模擬起算當年同時是退休年時，`applyYearEndAdjustment`算出一個不合理的巨大負值。根因是這個方法拿「退休後只有幾個月的小額年金稅」去跟「退休前真實發生的YTD薪資稅」相減——因為退休當年`effectiveAnnualSalary`目前被強制視為0。190原本提的方案是幫`TaxAdjustmentCell`這個前端元件加`isRetired`參數，依情境分流Tooltip文案。

190描述的這個觸發條件（模擬起算年同時是退休年），跟這份文件「差額最終在隔年透過確定申告結清」這一節討論的YTD落差，是同一個條件——只有起算年才有真實的YTD扣繳事實可以比較，未來任何一年退休都沒有這個落差需要處理。這份方向讓在職段改用真實所得重新計算稅負，而且確定讓算出來的差額（不管正負）都遞延到隔年才結清、不經過今年的`estimatedIncomeTax`等稅額欄位——這代表退休當年這一列，只會顯示在職段用真實所得算出來的正常稅負，不會再有任何因為跟YTD比較而產生的負數。190原本要處理的「這一列顯示不合理巨大負值、Tooltip文案對不上退休情境」，這個前提本身不會發生。

隔年也不會重生同樣的問題：遞延的差額直接加進`currentLiquidCash`現金欄位，不經過`estimatedIncomeTax`這三個稅額欄位，不會觸發`TaxAdjustmentCell`。**這代表issue-190不需要照它原本提的「依isRetired分流Tooltip文案」方案去修——190描述的情境在這份方向落地後直接消失，是被這份方向取代解決，不是另外獨立修好的。**issue-190.md本身的狀態（要不要標記成由這份方向解決）留給之後決定。
