# Plan 18-01：Chrome Extension重新匯入時，用「DB現有值 vs 頁面最新值」逐欄位比對預覽畫面，把要保留誰的決定權交給使用者，不要讓後端自己猜

## 這份文件怎麼來的
這是在討論job import reimport時逐欄位merge規則（現在記錄在[issue-180](../pending%20fix/issue-180.md)及其附屬issue）時，針對「保單」這個領域（`policyName`/`annualPremium`/`endDate`這三個欄位同時可以被使用者手動改、也會被重新匯入覆寫，不是單純的「使用者欄位vs事實欄位」二選一能處理的情況）衍生出的討論。原本考慮的方向是「匯入來源的紀錄整張唯讀，只有使用者自己手動新增的紀錄才能改」，但使用者進一步想清楚後，提出一個更根本的替代方案：不在後端猜測「這個欄位該不該被覆寫」，而是在[Plan-18](Plan-18-chrome-extension-data-extractor.md)的Chrome Extension重新匯入流程裡，加入一個讓使用者逐欄位確認的預覽畫面，把決定權交還給使用者本人。

## 範圍界定：這個設計只適用於「未來透過Extension送資料進來的其他使用者」，不影響現在的資料夾掃描式匯入
使用者明確說明：這個系統目前唯一的開發者兼使用者（也就是使用者本人），日常匯入資料的方式是透過後端資料夾掃描式匯入（`XxxJobServiceImpl`那一整套，掃描使用者自己放進容器掛載資料夾裡的HTML/CSV檔案），搭配「跑reset清空重新匯入全部資料再跑模擬」這種開發迴圈，使用者本人很清楚這套流程的限制，不需要、也不會透過這個預覽畫面去操作。

這個預覽/確認機制要解決的，是未來其他使用者（例如配偶、長輩，見[Plan-02](Plan-02-多使用者架構、家族共享與隱私控制.md)、[Plan-03](Plan-03-家族財務服務與模擬器整合.md)）透過[Plan-18](Plan-18-chrome-extension-data-extractor.md)的Chrome Extension送資料進來這條路徑——這些使用者沒有辦法SSH進容器放檔案，唯一能用的匯入途徑就是Extension。

## 設計方向：由Extension在送出前讓使用者逐欄位確認，後端只接收使用者確認過的最終值
流程如下：

1. 使用者在瀏覽器裡開啟某個金融網站頁面（例如保單頁面），Extension偵測到頁面並準備抽取資料。
2. Extension送出前，先呼叫後端對應的GET端點，拿到資料庫裡這筆紀錄目前的完整現有值。
3. Extension把「資料庫現有值」跟「這次從頁面抽取到的最新值」逐欄位比對，畫出一個預覽畫面，標示出哪些欄位的值不一樣。
4. 每個不一樣的欄位旁邊有一個「保留現有值」的勾選框，讓使用者自己決定：這個欄位要維持資料庫裡原本的值，還是要採用這次從頁面抓到的新值。
5. 使用者確認完畢後送出：有勾選「保留」的欄位，Extension送出的是資料庫原本的值；沒有勾選的欄位，送出的是這次抓到的新值。
6. 後端收到的，永遠是一包「使用者已經確認過的最終結果」，不需要在Service/merge層對任何欄位做「這個該不該fallback」的判斷。

## 這個機制解決的是哪一層問題：跟job import的merge規則是互補關係，不是取代關係
這點容易被誤解，先講清楚：[issue-180](../pending%20fix/issue-180.md)系列定案的merge規則（每個欄位分類成「使用者輸入」或「匯入事實」兩類，merge時二選一覆蓋或保留）**沒有被這份文件取代**，房貸、銀行/信用卡、訂單項目這類「使用者輸入欄位」跟「匯入事實欄位」本來就是兩組完全不同欄位的案例，用merge規則處理這件事依然成立、依然是正確的方向——這份文件完全不影響這一層。

這份文件解決的是另一層、更窄的問題：像保單`policyName`/`annualPremium`/`endDate`這種**同一個欄位、兩種來源都有資格寫**的情況（不是「使用者欄位」跟「事實欄位」是兩組不同欄位，是同一組欄位本身就可能同時存在「使用者之前手動改過的版本」跟「這次匯入抓到的新版本」）。issue-180系列的merge規則本質上是「這個欄位parser拿不到就保留、拿得到就覆蓋」的二選一判斷，沒辦法處理「parser明明拿得到、但使用者可能也剛好手動改過」這種雙方都有資格寫的情況——這才是Extension預覽機制真正要解決的事：把「這次該聽誰的」這個決定，從後端的猜測，變成使用者在送出前的明確選擇。

換句話說：
- **一般欄位的merge規則**：由issue-180系列的設計決定（parser拿得到就覆蓋、拿不到就保留DB現有值）。
- **同一欄位兩邊都想寫時聽誰的**：由這份文件的Extension預覽機制決定，發生在「送出前」這個時間點，不是後端merge邏輯的事。
- 兩者分工清楚、互相獨立，不衝突。

## 跟job import merge規則既有內容的關係
- 這份文件不影響[issue-180-02](../pending%20fix/issue-180-02.md)**銀行/信用卡交易**這個已經定案的領域——銀行/信用卡交易一旦成立就不會再變動，不存在「同一欄位、兩種來源都想寫」的情況，不需要這套checkbox機制。但**房貸**（[issue-180-01](../pending%20fix/issue-180-01.md)）在這份文件的適用範圍內：房貸餘額、利率這類會隨每月對帳單變動的帳戶層事實欄位，如果未來改由Extension連接，可以套用這套逐欄位checkbox機制；現階段房貸仍走後端資料夾掃描式匯入，這個機制尚未實際接線，merge規則也不受影響。
- 這份文件直接影響**保單**這個領域（`policyName`/`annualPremium`/`endDate`同一欄位兩種來源都能寫的那個混合問題）：一旦保單的資料來源之一改成透過Extension送進來（Plan-18的`支援站點策略`裡尚未定案優先順序），這個領域不適用issue-180系列的二選一merge規則；這份文件要解決的正是這個落差——同一組欄位兩邊都有資格寫時，由Extension預覽機制讓使用者在送出前決定最終值，不需要在後端另外設計一套判斷邏輯。
- 其他領域（訂單項目、NISA），如果這些資料來源之後也改由Extension送進來，一樣可以套用這個機制處理「同一欄位兩邊都想寫」的情況，但這跟job import的merge規則、商務ID怎麼找是各自獨立的事，不互相取代。

## 這份文件沒有決定的部分
- Extension預覽畫面的具體UI設計、勾選框的預設狀態（預設保留現有值、還是預設採用新值）。
- 後端對應的GET端點，是否需要新增專門給Extension比對用的回應格式，還是沿用現有的GET端點。
- 哪些領域的資料來源會優先改成透過Extension送進來——這點由[Plan-18](Plan-18-chrome-extension-data-extractor.md)的`支援站點策略`決定，這份文件不代為排序。
