# WONTFIX 09：保費扣除沒分新舊制度，舊保單保戶的模擬扣除額會算錯

## 判定：WONTFIX（2026-09-15）
**理由**：使用者本人名下沒有任何2011年12月31日以前簽約的舊制保單，沒有實際資料可以驗證。這個系統目前是為了下個月的貸款決策趕著跑模擬用的個人工具，不是要開放給其他使用者的產品，頂多之後放上GitHub讓有需要的人自己修改。在沒有真實舊制保單需要試算、也沒有其他使用者的情況下，現在花力氣做這件事沒有實際效益。

---

## 嚴重程度
Medium——只影響2011年12月31日以前簽訂的舊制人壽保險保單，但一旦適用，會讓保費扣除額被系統性低估，使得應稅所得試算偏高、可支配現金試算偏低。

## 現狀
日本的人壽保險保費扣除額，依保單簽約日期分成「新制」（2012年1月1日以後簽約）跟「舊制」（2011年12月31日以前簽約）兩套完全不同的公式，換算出來的扣除額金額不一樣。目前系統裡的保費扣除額計算，只有新制這一套公式，完全沒有實作舊制公式，也沒有任何欄位讓使用者填寫保單的簽約日期，導致系統無法判斷、也無法選擇該用哪一套公式。所有舊制保單的保戶，模擬出來的保費扣除額都會被誤用新制公式去計算。

## 原因
`ActiveTaxCalculationEngine.java` 第242-264行的兩個計算方法：

```java
// calculateLifeInsuranceDeductionIncomeTax(premium)：
//   保費≤20,000元：全額扣除
//   保費≤40,000元：保費/2 + 10,000
//   保費≤80,000元：保費/4 + 20,000
//   保費>80,000元：固定上限40,000
// calculateLifeInsuranceDeductionInhabitantTax(premium)：
//   保費≤12,000元：全額扣除
//   保費≤32,000元：保費/2 + 6,000
//   保費≤56,000元：保費/4 + 14,000
//   保費>56,000元：固定上限28,000
```

這兩組門檻數字，精準對應日本「2012年1月1日以後簽約」（新制）的保費扣除公式。整個程式碼裡完全沒有「舊制」（2011年12月31日以前簽約）的公式，也沒有任何邏輯依簽約年度去選擇該用哪一套、或是兩套都算然後取對保戶較有利的一邊——因為從資料模型層（`InsurancePolicy.java`）、後端API請求層（`InsurancePolicyRequest.java`）、到前端型別（`types.ts`）、前端表單（`insurance-dialog.tsx`），這4個層級都完全沒有「簽約日期」這個欄位，系統從資料輸入的最源頭就沒有蒐集這項資訊，自然也就無從判斷。

## 具體錯誤情境
使用者持有一份2008年簽約的終身壽險（舊制保單），年繳保費90,000元，目前仍在繳費中。依真實的舊制公式，保費在50,000元到100,000元之間的計算方式是「保費/4 + 25,000」，算出來應該是90,000/4 + 25,000 = 47,500元。但系統目前套用新制公式：90,000元超過新制的80,000元門檻，被固定上限鎖在40,000元。結果系統算出來的扣除額比真實金額少了7,500元，導致應稅所得被高估、可支配現金被低估；如果使用者持有多筆或金額更大的舊制保單，這個落差會持續累積放大。

## 建議修正
以下三個方向各有取捨：

**方向A：幫保單新增「簽約日期」或「新舊制度」欄位，依此分別套用新制或舊制公式**
- 優點：最準確，能正確反映真實情況。
- 缺點：需要同時修改資料庫結構、後端API、前端表單這三個層級；而且如果使用者同一年度同時持有新制跟舊制保單，還需要額外設計更複雜的「新舊制合併上限」計算邏輯，實作與測試成本都比較高。

**方向B：維持只有新制公式，但在保單輸入畫面加上明確的警告文字，說明「本工具目前只能正確計算2012年以後簽約的保單，2012年以前簽約的保單試算結果可能不準確」**
- 優點：不需要改動任何計算邏輯或資料結構。
- 缺點：如果使用者沒注意到這段警告文字、或根本不確定自己保單的簽約年度，這個問題依然會發生，系統本身也沒有任何機制能自我偵測或校正這個落差。

**方向C：完全改變輸入方式——讓使用者自己輸入已經算好的「可扣除金額」，而不是輸入「年繳保費」，把新舊制換算的工作交給使用者自己處理**
- 優點：實作最簡單。
- 缺點：完全失去這個工具原本「自動幫使用者換算保費扣除額」的價值，而且會讓這個保單類型要填的欄位（要填「扣除金額」）跟其他保單類型（都是填「保費」）不一致，使用起來不直覺。
