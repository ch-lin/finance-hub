# WONTFIX 27：全面廢除向當前時間補算（Fast-Forward / Catch-Up）機制，模擬起點一律維持快照原始時間點

## 判定：永久廢止 / 駁回（WONTFIX / Invalid by Architectural Design，2026-10-01 決策確立）

本項目正式確立並收錄系統核心架構鐵則：**「全面廢止任何資產類別向當前時間點進行歷史補算（Fast-Forward / Catch-Up）的機制。資產模擬起點一律嚴格錨定在使用者最後一次上傳快照的原始時間點本身，不做任何時間推算，亦不嘗試跳躍至今日。」**

本判定永久終結了先前在 **Issue 104**、**Issue 105** 以及 **Feature Requirement 132（[Fixed-132](../fixed/Fixed-132.md)）** 中反覆探討的「補算到現在」邏輯，將「跨期補算」正式定性為違反財務真實性與工程邊界的反模式（Anti-Pattern）。

## 歷史提案與問題演進

1. **起點（Issue 104 的局部視角）**：
   系統最初存在 `fastForwardMortgagesToPresent` 機制。若使用者上次匯入房貸紀錄是 6 個月前，系統會在進入模擬前，自作聰明地依序逐月遞減房貸本金，試圖將餘額「快轉」到本月。在 Issue 104 中，發現該演算法在補算歷史月份時誤用了使用者在 Sandbox 填寫的未來假設利率（如 5.0%），而非合約真實利率（0.5%）。最初的修正方向僅僅是將利率來源改為合約利率。

2. **擴大（Issue 105 的對稱性追求）**：
   隨後在 Issue 105 中，觀察到房貸有快轉，但銀行現金、NISA、iDeCo、股票等資產卻維持舊快照，產生了「單邊時間旅行」的時間基線不對齊。提案者因而提議：既然 NISA 與 iDeCo 擁有定期定額扣款設定，應該也為 NISA 與 iDeCo 實作向當前時間的補算邏輯。

3. **轉折與徹底推翻（Fixed-132 的深層架構反思）**：
   在深入審查 Issue 105 實作可行性時，開發團隊與使用者發現：試圖在多個孤立帳戶之間用公式進行「歷史補算」，在會計學、系統責任與物理現實上存在無法跨越的致命缺陷。使用者拍板做出根本性決策——**不是幫其他資產補上補算，而是把既有的房貸補算連根拔除，全系統六大資產類別一律不准補算**。

## 駁回補算機制的五層核心架構論證

這項 WONTFIX 決策並非工程資源不足的妥協，而是基於深思熟慮的五層嚴密邏輯推論：

### 第一層：責任歸屬與確定性謊言（Liability vs. Grounded Facts）
系統使用確定性的數學公式去替使用者斷言一段「使用者沒有告訴系統的真實歷史」（例如：上次上傳對帳單到今天之間，真實世界到底發生了什麼）。
- 若 AI 出錯，使用者尚可理解為機率性誤差；但系統核心引擎用確定性邏輯斷言了一個與真實銀行帳戶不符的虛構數字，一旦出錯，責任將完全由系統與開發者承擔。
- **純 FP 現金流模擬，無對接 LLM「腦補」資料之意圖**：本系統核心定位僅為 FP（理財規劃，Financial Planning）計算與模擬現金流的狀況，並無直接跟 LLM 對接進行「腦補」或生成歷史資料的意圖與架構。FP 計算仰賴嚴謹的數理規則與客觀事實輸入，絕不容許透過任何推演模型對未知的歷史空窗期進行無依據的腦補填空。
- **無權限亦無責任猜測意圖**：系統無權限也無責任幫使用者猜測上傳舊版快照或是資料的意圖。使用者上傳較舊的快照或資料，可能是為了回溯特定歷史時間點的資產配置、進行基準日情境回測，或者只是單純尚未匯入最新對帳單。無論使用者動機為何，系統的職責是忠實反映該筆輸入資料所代表的客觀事實，絕無權限越俎代庖、自作主張替使用者「補算到今天」。
- **核心立場**：系統絕不代替使用者捏造事實。「使用者 upload 什麼就是現在的事實。」

### 第二層：缺乏客觀可靠的時間基準點（Lack of a Verifiable Baseline Timestamp）
即便在數學上想做補算，系統也無法確定使用者匯入檔案的精確真實時間點：
- 各金融機構匯出的 HTML 或 CSV 內文往往缺乏全球統一的絕對時標。
- 使用者可能分好幾天陸續下載不同資產的對帳單，也可能將一週前下載的離線檔案延遲匯入。
- 若輸入源本身就缺乏同步的時間基準，任何基於「距離今天過了 N 個月」的補算公式，其輸入參數從一開始就是不著邊際的空中樓閣。

### 第三層：跨帳戶金流與實體現金斷點無法透視，系統絕不當會計查帳員（Physical Cash Breakpoints & Audit Nightmare）
任何試圖對齊跨帳戶金額的補算，都會不可避免地陷入會計稽核與查帳泥淖：
- **扣款與入帳不對等**：銀行扣除的定期定額投資款，並不等於證券端當月成功買入基金的份額（存在交易手續費、外匯買賣價差、休假日延遲交割與分批扣款）。
- **實體現金斷點與資金挪移**：使用者可能因 A 銀行房貸餘額不足，從 B 銀行甚至海外帳戶領出現金臨櫃補入；或透過 ATM 提領實體紙鈔消費。
- 系統沒有全域的複式簿記（Double-Entry Bookkeeping）交易明細，無法透視實體紙鈔的流動軌跡。要完美補算，等同於要具備國稅局查帳員的全面稽核能力。
- **工具定位澄清**：本系統僅為「純 FP 長線現金流模擬與破產風險評估工具（Long-term Cash Flow Bankruptcy Evaluation Tool）」，絕非「會計對帳與稅務稽核軟體」，更無直接藉由 LLM 介入腦補金流數據的機制。

### 第四層：致命之憑空印鈔（Ghost Money）與雙重扣款（Double Counting）
既有的房貸補算機制（`fastForwardMortgagesToPresent`）揭露了補算演算法無法克服的內在矛盾：
- **憑空印鈔**：房貸補算每跑一個月，房貸本金就減少數萬日圓，但**銀行帳戶的現金完全沒有同步扣減**！這導致模擬起始點平白虛增了數十萬至數百萬日圓的淨資產。
- **雙重扣款**：若系統自作聰明連動扣除銀行現金，當使用者日後匯入最新真實銀行對帳單（該對帳單已包含該筆房貸扣款）時，系統將引發「前次補算扣一次、真實對帳單又扣一次」的二度扣款災難。
- NISA/iDeCo 若套用補算，亦會在證券與銀行之間造成相同的幽靈資金或重複計算問題。

### 第五層：單一真理來源（Single Source of Truth, SSOT）
所有試圖「快轉到今天」的微調與小聰明，本質上都是對「資料新鮮度不足」這一現實問題的錯誤工程回應。
- 使用者若追求最高精準度的模擬起點，**唯一的正道是重新匯入最新對帳單**，而不是依賴系統的通靈公式進行補算。
- 系統在使用者按下模擬的那一刻，誠實、忠實地採用當下所持有的快照數據推算未來，才是最健康且無副作用的架構設計。

## 最終處置與系統現行規範

依據上述五層論證，全案於 Fixed-132 正式收斂並落地為下列永久架構規範：

1. **後端計算引擎完全純淨化**：
   - 徹底刪除 `MortgageCalculator.fastForwardMortgagesToPresent` 及其所有依賴。
   - 拒絕在 `NisaContextBuilder`、`DefinedContributionContextBuilder` 或任何其他資產 Builder 中實作任何補算邏輯。
   - 房貸、銀行現金、NISA、iDeCo、公司股票、年金、DC 企業型等所有資產，一律以快照原生餘額作為起始點。

2. **前端職責回歸透明度提示**：
   - 前端不再宣稱「系統會自動補算到當前月份」。
   - UI 僅單純展示「資料新鮮度提示（Data Freshness Banner）」，客觀呈現快照落後月數，並由使用者自行決定是否更新對帳單。

3. **歷史 Issue 正式收束**：
   - **Issue 104**：隨著 `fastForwardMortgagesToPresent` 整段刪除，其「誤用假設利率」之子問題隨母體消失而自然結案，無需獨立維護。
   - **Issue 105**：原提案中「NISA/iDeCo 補算」方向永久駁回（WONTFIX）；僅保留「資產新鮮度提示」之 UX 需求。

## 結論與不可動搖之架構鐵則

> **「上傳什麼就是什麼。本系統僅為 FP 計算模擬現金流的狀況，並無直接跟 LLM 對接進行『腦補』該資料的意圖，亦不搞通靈補算、不當會計查帳員。系統無權限也無責任幫使用者猜測上傳舊版快照或是資料的意圖。使用者若要最精準的模擬起點，唯一的正道是重新匯入最新對帳單。」**

凡任何試圖重新引入「跨期歷史補算」、「自動推算空窗期餘額」、「單邊時間跳躍」之功能提案，一律依據本 WONTFIX 判定逕行駁回。
