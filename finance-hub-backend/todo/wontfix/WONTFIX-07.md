# WONTFIX 07：背景job自動匯入薪資單永遠誤判成月薪，即將被Chrome extension的預覽確認流程取代

## 判定：WONTFIX（2026-09-15）
**理由**：這是背景job，跟issue-34的Sony銀行房貸匯入一樣，之後會被Chrome extension取代整個刪除。改用extension之後，匯入流程會變成「先預覽、使用者確認後再送出job」，屆時使用者自己就能在預覽畫面上看到並修正這筆薪資單被系統判斷成哪一種類型，不需要現在為了一個即將被取代的背景job決定該用哪一種修法方向。

---

## 修正說明（2026-09-15）
使用者確認：手邊沒有任何一張真正的獎金（賞与）薪資單，實際領的是commission（按業績抽成），只有commission形式的薪資單樣本——沒有任何管道可以確認一張真正的獎金單，欄位／關鍵字會長什麼樣子。

這代表下方「建議修正」的**方向A（解析HTML時自動判斷是不是獎金單，用檔名或關鍵字如「賞与」「ボーナス」）目前無法驗證、也無法實作**——不是先跳過驗證這一步之後再實作，是根本沒有樣本可以確認關鍵字是否存在、格式長什麼樣，貿然寫死關鍵字等於用猜的，違反「千萬不要用猜的」的原則。除非之後拿到真實的獎金單樣本，方向A都不該被採用。

實際可行的方向縮小為方向B（匯入後由使用者手動確認類型）跟方向C（維持現狀、只補說明文字），這裡不代為決定要選哪一個。

## 嚴重程度
Medium — 這個問題不會直接讓房貸攤還或稅務試算本身算錯數字，但它會讓「使用歷史獎金資料試算未來獎金收入」這個設定，對只靠自動匯入薪資單的使用者形同壞掉（永遠抓不到任何一筆獎金紀錄），也會讓「每月平均薪資」這個作為未來薪資試算基礎的數字，混入本來該算成獎金的金額。這兩個數字都會餵進整體現金流與淨資產試算的收入假設，房貸破產模擬的核心正是「未來現金流夠不夠付房貸」，收入基礎被算錯會間接影響核心模擬結果的可信度；但因為只有「自動匯入路徑」受影響（手動輸入不受影響），且平均薪資被拉高或拉低的方向目前無法確認，所以評為 Medium 而非 High。

## 現狀
使用者如果讓系統自動處理薪資單HTML檔案來建立薪資紀錄——不管是排程自動匯入、還是在畫面上用「匯入單筆檔案」的功能——不管那張單子實際上是「當月薪資」還是「獎金/賞與」，系統都會把它存成「月薪」類型。只有使用者自己在畫面上手動新增或編輯一筆紀錄、並自己選擇「獎金」類別時，才會被正確標記成獎金。

這會影響到兩個地方：
1. 試算引擎有一個「使用歷史獎金資料試算」的設定，設計上是要依照過去真實入帳的獎金紀錄，去推算未來每年的獎金收入。但如果使用者是靠自動匯入薪資單累積資料，即使真的匯入了獎金單，系統也永遠抓不到任何一筆被標記成「獎金」的紀錄——這個設定對只用自動匯入的人來說形同無效。
2. 每月平均薪資的計算，也可能被一筆本來是獎金、卻被系統誤當成月薪計入的紀錄拉高或拉低（實際上會拉高還是拉低，要看真實獎金單HTML裡的欄位長怎樣，目前手上沒有真實獎金單樣本可以確認方向，所以這裡只能確認「會被混進去」這件事本身，不斷言方向）。

## 原因
`SalaryParserImpl.java` 解析HTML時，透過 `mapCoreField()`（第168-183行）與頁尾小計迴圈，把「基本給」「殘業手當」「健康保険料」「厚生年金保険料」「總支給」「差引支給額」等各種金額欄位逐一寫進 `SalaryRecord`，但整份程式碼（`parse()`、`mapCoreField()`、`extractDate()`）從頭到尾都沒有呼叫過 `record.setType(...)`。

`SalaryRecord.java` 第97行 `type` 欄位的預設值就是 `SalaryType.MONTHLY_SALARY`（月薪），所以只要沒有人主動設定，自動匯入的紀錄就會永遠停在這個預設值。

負責排程自動匯入（`execute()`，第119-149行）與畫面上單筆匯入（`processFile()`，第190-216行）的 `SalaryJobServiceImpl.java`，無論是新增紀錄、還是重新匯入覆蓋既有紀錄，這兩段程式碼裡逐欄位覆寫的清單（總支給、差引支給額、基本給、殘業手當、健康保険料……等）也一樣完全沒有處理「類型」這個欄位。

目前唯一會呼叫 `record.setType(command.getType())` 的地方，是使用者在畫面上手動新增/編輯紀錄時執行的 `SalaryRecordServiceImpl.java` 第97行——這條路徑會讓使用者自己選類別，所以手動輸入不會有這個問題。

下游的 `SalaryContextBuilder.java` 則是明確依照這個「類型」欄位分流計算：第62行只累加 `type == BONUS` 的紀錄來算近12個月獎金總額（`resolveAnnualBonusInfo`，供「使用歷史獎金資料試算」設定使用）；第134、151行只累加 `type == MONTHLY_SALARY` 的紀錄來算年度至今月薪基本給、以及計算平均月薪（`baseMonthlySalary = totalMonthlyIncome / monthlyRecordCount`）。兩條路徑算出來的結果完全不同，而自動匯入的紀錄因為 type 從頭到尾就等於預設值「月薪」，永遠只會走月薪那一條路。

## 具體錯誤情境
使用者這個月同時透過自動匯入拿到一張「當月薪資單」和一張「獎金單」（例如公司在7月同時發放月薪與夏季賞與，兩張都是HTML檔案）。系統排程自動匯入時，兩張單子都會被存成「月薪」類型的紀錄。

如果使用者接著打開「使用歷史獎金資料試算」這個設定，期待系統依照這張已經匯入的獎金單去推算明年的獎金收入，`SalaryContextBuilder.resolveAnnualBonusInfo()` 會去找 `type == BONUS` 的紀錄，但因為這筆紀錄實際存進去的類型是「月薪」，系統找不到任何一筆，等於這張獎金單完全沒有被試算引擎看到，試算結果跟使用者完全沒匯入過獎金單一樣。

同時，這筆本來是獎金的紀錄，因為類型變成「月薪」，會被 `initializeSalaryContext()` 的第134、151行一起算進「年度至今月薪基本給」跟「平均月薪」裡面——等於一筆獎金的金額，混進了本來應該只反映每月固定薪資的平均值計算。

## 建議修正
這個問題有幾種可能的修法方向，各有取捨，這裡不代為決定該採用哪一種：

- **方向A：解析HTML時自動判斷是不是獎金單。** 例如用檔名或內文關鍵字（像是「賞与」「ボーナス」）去判斷，符合就自動設成獎金類型。
  - 優點：全自動，使用者不用額外操作，體驗最順暢。
  - 缺點：需要真實獎金單HTML樣本才能確定這類關鍵字真的存在、格式長怎樣、而且不會誤判一般月薪單，這一點目前手上沒有真實獎金單樣本可以驗證，貿然套用有猜錯的風險。

- **方向B：匯入完成後，讓使用者自己確認一次。** 匯入時不自動猜測類型，但匯入完成後在畫面上提示使用者「這幾筆新匯入的紀錄請確認是月薪還是獎金」，讓使用者手動點選確認。
  - 優點：不會有猜錯類型的風險。
  - 缺點：多一道人工步驟，如果使用者略過這個確認畫面，原本的問題依然存在。

- **方向C：維持現狀，但把限制講清楚。** 自動匯入的紀錄一律先當成月薪，獎金一律仰賴手動輸入，但在「使用歷史獎金資料試算」這個設定旁邊加一行說明，講清楚「這個設定只會計入手動輸入的獎金紀錄」。
  - 優點：改動最小，不用動解析邏輯。
  - 缺點：沒有解決自動匯入本身「類型永遠猜錯」這個根本問題，只是讓使用者事先知道限制，使用者仍然無法只靠自動匯入拿到正確的獎金試算結果。

要選哪個方向，取決於使用者實際上是不是真的會用自動匯入去處理獎金單、以及願不願意接受多一道手動確認步驟，這些屬於產品使用方式的判斷，這裡不代為決定。

## 與已知項目的區別
現有清單中最接近的項目，是薪資歷史提取邏輯裡「月薪/獎金誤判、雙軌上限」相關的修正，但那次修正解決的是 `SalaryContextBuilder.java` 這個「消費端」的邏輯本身——也就是依 `type` 欄位分流累加月薪與獎金、以及把健保上限與厚生年金上限分成兩條各自計算——這部分程式碼現在讀起來邏輯是對的。

這次發現的問題是更上游的「生產端」問題：`SalaryParserImpl.java` 跟 `SalaryJobServiceImpl.java` 從頭到尾就不曾把任何一筆自動匯入紀錄的「類型」欄位寫回資料庫過，導致不管消費端（`SalaryContextBuilder`）的分流邏輯有多正確，自動匯入的紀錄永遠只會被分到「月薪」這一條路。這是既有修正之後仍然存在、且沒有被其他已知清單提到的殘留根因，屬於全新發現的問題，不是同一個已修好的項目。
